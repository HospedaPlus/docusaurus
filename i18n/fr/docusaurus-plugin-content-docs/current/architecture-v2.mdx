# Architecture v2

Voici l'architecture finale de HospedaPlus Revenue sur AWS (région **us-east-2, Ohio**) : trois EC2 avec Docker Compose, Kafka pour F2, Airflow 3.1.5 avec Celery sur RabbitMQ, Spark en mode local sur les workers, S3 + Athena (Glue Data Catalog rempli par DDL) et Power BI via ODBC.

## Changements par rapport à la version précédente

| Avant | Maintenant | Pourquoi |
| --- | --- | --- |
| Spark sur Fargate / EMR | **Spark local** sur l'EC2 des workers (t3.xlarge) | ~200 000 réservations tiennent sur une machine ; aucun cluster à payer ni à gérer |
| Amazon ECR | **GitHub Container Registry (GHCR)** | Les images sont construites par la CI à côté du code |
| Glue Crawler | **Athena DDL** (`CREATE EXTERNAL TABLE`) | Le compte n'autorise pas les crawlers ; le DDL donne des noms et types exacts |
| EKS, ALB, WAF, NAT, Secrets Manager | Non utilisés | Inutiles à cette taille ; les secrets sont dans des `.env` hors du dépôt et dans les secrets GitHub |
| Limites de surréservation calculées par l'exploitation | **Write-back de gold vers Neon** | L'exploitation utilise les mêmes taux d'annulation que le métier |
| Prix F2 via RabbitMQ | **F2 via Kafka** vers Neon | RabbitMQ n'est que le broker de Celery |
| Kafka et simulateurs dispersés | Un **EC2 des sources** | Une machine pour tous les simulateurs |

## Bloc par bloc

### 1. Sources et équipe

- **Équipe dev · GitHub Actions** : ruff, pytest et validation des DAGs ; à chaque merge, une image est poussée sur GHCR et déployée par SSH.
- **Équipe data** : se connecte aux machines en SSH et ouvre les UIs d'Airflow (`:8080`) et de Flower (`:5555`).
- **Producteur F2** (événements OTA, contrat 1.3) et **simulateur F3** (`seed simulate`, réservations directes, rôle `app_writer`).
- **APIs F5 · F6 · F7** : l'API d'avis de l'équipe (FastAPI sur ECS), Nager.Date et Frankfurter, lues en HTTPS.
- **F1 Kaggle** : `hotel_bookings.csv` du dépôt `hospedaplus-csv`, chargé une fois.
- **Catalogue partagé** : la source canonique est `db_simulated` (Neon) ; F2, F4 et F5 utilisent ses codes d'hôtel, de type de chambre, de canal et de devise.

### 2. Entrée

- **GHCR** stocke les images (`ghcr.io/hospedaplus/…`, tags `:sha`, `:main` et `vX.Y.Z`).
- **Internet Gateway** vers le VPC (sous-réseau public, IP publiques).
- **Security groups** : `sg-nucleo` ouvre 22, 8080, 5555 et 15672 seulement à l'IP de l'équipe, 80/443 pour Nginx (les [UIs de supervision](./data-engineering-pipeline/monitoring.mdx)), et 5432, 5672 et 8080 seulement à `sg-workers` ; `sg-workers` ouvre 22 à l'équipe. Les workers joignent le cœur par son **IP privée**.

### 3. Traitement : EC2 en us-east-2

- **EC2 des sources** (Docker Compose) : `buenavista-streaming` (producteur F2 → **Kafka 4.1.1**, topic `reservation.events.v1_3`, 6 partitions + DLQ → 6 `neon-consumer` qui appellent `reservar()`), `db_simulated` (F3 `seed simulate`) et `hospedaplus-csv` (`f4-weekly`, lundi 06:00 UTC, 15 agences → S3 et Neon).
- **EC2 cœur** (t3.medium, 30 Go) : Airflow 3.1.5 avec CeleryExecutor (API server, scheduler, DAG processor, triggerer, PostgreSQL de métadonnées), RabbitMQ (files `bronze`, `silver`, `gold`) et Flower.
- **EC2 workers** (t3.xlarge, 50 Go) : trois workers Celery. **bronze** exécute 4 tâches à la fois (Python : Neon, APIs F5–F7, F1 et F4 → `bronze/`) ; **silver** en exécute 2 (Spark local : valide, dédoublonne, convertit en COP) ; **gold** en exécute 2 (Spark local : `dim_`, `fact_`, `mart_` P1–P5 et le write-back). Spark 3.5 lit et écrit S3 avec `s3a://` grâce au rôle IAM de l'EC2. Détails dans [Calcul et ressources](./data-engineering-pipeline/compute-resources.mdx).

### OLTP : Neon PostgreSQL (SaaS externe)

Schémas `operation` et `streaming`, branches `development` et `production`, et `reservar()` avec la limite de surréservation (0 aujourd'hui). Le pipeline la lit avec `etl_reader` chaque heure et par une copie complète à 03:00 UTC, et y réécrit les taux d'annulation avec `app_writer`.

### 4. Data lake (OLAP)

- **Amazon S3 `hospedaplus-lakehouse-buenavista`**, accès public bloqué : `bronze/` (JSON/CSV tels qu'extraits), `silver/` (Parquet : réservations, annulations, occupation, calendrier, avis, change, historique F1), `gold/` (Parquet : 4 dims, 4 facts, 7 marts, et un JSON pour le write-back vers Neon), `airflow-logs/` et `athena-results/`.
- Chaque DAG publie un **Asset** à la fin et le suivant démarre seul.
- **Athena DDL → Glue Data Catalog** (`hospedaplus_gold`, rejoué seulement si un schéma change) → **Amazon Athena** (workgroup `primary`).

### 5. Analyse et décision

**Power BI Desktop** lit gold avec le pilote ODBC Amazon Athena (x64) sous l'utilisateur IAM en lecture seule `powerbi-reader` ; le rapport a 4 pages. Le **Revenue Manager et les directeurs d'hôtel** l'utilisent pour décider des prix et de l'occupation par hôtel. Voir [Visualisation des données](./data-visualization/index.mdx).

## Sécurité et exploitation : ce qui est configuré aujourd'hui

| Domaine | Ce qui est en place |
| --- | --- |
| IAM | Rôle `hospedaplus-pipeline-role` sur le cœur et les workers, limité au bucket. Utilisateur `powerbi-reader` : Athena, Glue et S3 en lecture. |
| Security groups | `sg-nucleo`, `sg-workers` : ports ouverts seulement à l'IP de l'équipe et entre les deux groupes. |
| Identifiants | `.env` sur chaque EC2 (hors du dépôt), secrets de déploiement dans GitHub, clés AWS vides (fournies par le rôle). |
| Rôles Neon | `hospedaplus_owner` (migrations), `app_writer` (consommateurs, simulateurs, write-back), `etl_reader` (Airflow). |
| S3 | Accès public bloqué ; logs Airflow dans `airflow-logs/`, résultats Athena dans `athena-results/`. |
| Supervision | Flower pour les workers, l'UI Airflow, `docker compose logs` et le lag du groupe Kafka. Voir [Supervision](./data-engineering-pipeline/monitoring.mdx). |

## Flux de données (légende)

- **Temps réel / OLTP (rose) :** événements F2 via Kafka et chargements F3/F4 qui appellent `reservar()` dans Neon.
- **CI/CD et contrôle (violet, pointillé) :** images dans GHCR, déploiement par SSH, ordres Airflow via RabbitMQ.
- **Batch / OLAP (bleu) :** extraction vers bronze, puis bronze → silver → gold (workers Celery + Spark local).
- **Catalogue (bleu-vert, pointillé) :** tables créées par Athena DDL dans le Glue Data Catalog (sans crawler).
- **Write-back (orange) :** gold → Neon `operation.cancellation_rate_by_lead` (upsert quotidien).
- **Consommation de gold (vert) :** Athena → Power BI (ODBC) → directeurs.
- **En attente (gris, pointillé) :** API métier avec FastAPI (US-41).
