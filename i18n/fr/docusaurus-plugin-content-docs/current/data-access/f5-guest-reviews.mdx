# <SourceTitleIcon icon="message" tone="purple" />F5 · Avis clients <SourceType>API REST</SourceType>

## Comment y accéder

L'API est publique et ne demande aucun jeton. Sa documentation interactive (Swagger UI) se trouve sur [`/docs`](https://api-reviews-buenavista.coderhivex.com/docs), et le contrat OpenAPI sur [`/openapi.json`](https://api-reviews-buenavista.coderhivex.com/openapi.json).

- **URL de base :** `https://api-reviews-buenavista.coderhivex.com`
- **Préfixe de l'API :** `/api/v1`
- **Dates et heures :** toujours en UTC, au format ISO 8601.

### Endpoints

| Méthode | Chemin | Rôle | Codes de réponse |
| --- | --- | --- | --- |
| `GET` | `/api/v1/reviews` | Liste paginée des avis, avec filtres | 200, 422 |
| `GET` | `/api/v1/reviews/{review_id}` | Un avis par son id | 200, 404 |
| `POST` | `/api/v1/reviews` | Crée un avis | 201, 409, 422 |
| `PATCH` | `/api/v1/reviews/{review_id}` | Met à jour partiellement un avis (`rating`, `title`, `text`, `language`) | 200, 404, 422 |
| `DELETE` | `/api/v1/reviews/{review_id}` | Supprime un avis | 204, 404 |
| `GET` | `/api/v1/hotels` | Catalogue des 28 hôtels utilisés par les avis | 200 |
| `GET` | `/health` | Contrôle de vie, utilisé par le répartiteur de charge | 200 |
| `GET` | `/health/ready` | Contrôle de disponibilité, vérifie la connexion à la base de données | 200, 503 |

La plateforme de données ne fait que lire : elle utilise `GET /api/v1/reviews` et `GET /api/v1/hotels`. Les endpoints d'écriture permettent à l'équipe de tester des cas limites, comme un avis modifié ou supprimé.

### Filtres et pagination

`GET /api/v1/reviews` accepte ces paramètres de requête, tous facultatifs :

| Paramètre | Type | Description |
| --- | --- | --- |
| `page` | entier ≥ 1 | Numéro de page. Par défaut `1`. |
| `page_size` | entier 1–100 | Avis par page. Par défaut `50`, maximum `100`. |
| `hotel_id` | texte | Code de l'hôtel, par exemple `HP-CO-001`. Les codes viennent de `/api/v1/hotels`. |
| `platform` | `booking`, `google`, `tripadvisor`, `expedia` | Plateforme sur laquelle l'avis a été publié. |
| `language` | `es`, `en`, `pt` | Langue de l'avis. |
| `min_rating`, `max_rating` | entier 1–5 | Plage de notes, bornes incluses. |
| `published_from`, `published_to` | date `YYYY-MM-DD` | Plage de dates de publication en UTC, bornes incluses. |
| `order` | `asc`, `desc` | Tri par `published_at` puis par `id`. Par défaut `asc`. |

Les résultats sont toujours triés par `published_at` puis par `id`, donc les pages ne se chevauchent jamais et ne sautent aucun avis tant que les données ne changent pas.

### Ingestion quotidienne

Pour charger une journée, appelez la liste avec `published_from` et `published_to` égaux à ce jour, et parcourez les pages tant que `pagination.has_next` vaut `true`.

<Tabs groupId="f5-client">
<TabItem value="curl" label="curl" default>

```bash
curl "https://api-reviews-buenavista.coderhivex.com/api/v1/reviews?published_from=2026-09-30&published_to=2026-09-30&page=1&page_size=100"
```

</TabItem>
<TabItem value="python" label="Python">

```python
import requests

BASE_URL = "https://api-reviews-buenavista.coderhivex.com/api/v1/reviews"


def load_day(day: str) -> list[dict]:
    """Return every review published on one UTC day (YYYY-MM-DD)."""
    reviews, page = [], 1
    while True:
        response = requests.get(
            BASE_URL,
            params={"published_from": day, "published_to": day, "page": page, "page_size": 100},
            timeout=30,
        )
        response.raise_for_status()
        body = response.json()
        reviews.extend(body["items"])
        if not body["pagination"]["has_next"]:
            return reviews
        page += 1


reviews = load_day("2026-09-30")
```

### Erreurs

Les erreurs dues à une règle métier ont toutes la même forme, avec un code dans `error` et un message dans `detail` :

```json
{ "error": "not_found", "detail": "Review 99999 not found" }
```

| Code | `error` | Quand cela arrive |
| --- | --- | --- |
| 404 | `not_found` | L'id de l'avis n'existe pas. |
| 409 | `conflict` | Un avis avec la même `platform` et le même `external_id` existe déjà. |
| 422 | `business_rule_violation` | Une règle n'est pas respectée : `published_from` est après `published_to`, `min_rating` est supérieur à `max_rating`, l'hôtel n'existe pas, `published_at` est dans le futur ou `stay_date` est après `published_at`. |
| 422 | (format FastAPI) | Un paramètre ou un champ a un type incorrect ou est hors limites. |
| 500 | `internal_error` | Erreur inattendue sur le serveur. |

## Contenu

Chaque avis contient ces champs :

| Champ | Type | Description |
| --- | --- | --- |
| `id` | entier | Id interne de l'avis dans l'API. |
| `external_id` | texte | Id de l'avis sur sa plateforme. Il commence par le préfixe de la plateforme : `BK-`, `GG-`, `TA-` ou `EX-`. |
| `platform` | texte | `booking`, `google`, `tripadvisor` ou `expedia`. |
| `hotel_id` | texte | Code de l'hôtel dans le catalogue partagé, par exemple `HP-CO-001`. |
| `language` | texte | `es`, `en` ou `pt`. |
| `rating` | entier | Note normalisée sur une échelle de 1 à 5. |
| `title` | texte, facultatif | Titre court de l'avis, jusqu'à 150 caractères. |
| `text` | texte | Corps de l'avis, jusqu'à 5 000 caractères. |
| `reviewer_name` | texte | Nom du client. C'est une donnée personnelle. |
| `reviewer_country` | texte, facultatif | Pays du client, sous forme de code ISO à 2 lettres. |
| `stay_date` | date, facultatif | Date du séjour. Elle n'est jamais postérieure à la date de publication. |
| `published_at` | date et heure (UTC) | Moment où l'avis a été publié sur la plateforme. |
| `created_at`, `updated_at` | date et heure (UTC) | Moment où l'avis a été créé et modifié pour la dernière fois dans l'API. |

La paire `platform` + `external_id` est unique : une plateforme ne répète jamais son propre id d'avis.

### Plateformes et langues

Les avis se répartissent entre les plateformes selon ces proportions :

| Plateforme | Part | Préfixe de `external_id` |
| --- | --- | --- |
| Booking | 40 % | `BK-` |
| Google | 30 % | `GG-` |
| Tripadvisor | 20 % | `TA-` |
| Expedia | 10 % | `EX-` |

La langue dépend du pays de l'hôtel. Par exemple, les hôtels de Colombie, du Mexique et d'Espagne reçoivent surtout des avis en espagnol, et les hôtels du Brésil et du Portugal reçoivent surtout des avis en portugais. Environ un avis sur cinq est en anglais.

### Notes et textes

Chaque hôtel a sa propre qualité moyenne, entre 3,2 et 4,6 étoiles, donc certains hôtels sont mieux notés que d'autres. Les plus grands hôtels, avec plus de chambres, reçoivent plus d'avis.

Les textes sont construits à partir de phrases sur des thèmes récurrents, pour que l'analyse de réputation puisse les repérer : propreté, personnel, emplacement, petit-déjeuner, bruit, wifi, check-in, rapport qualité-prix, la piscine (seulement dans les hôtels resort) et le relogement dans un autre hôtel. Un avis de 4 ou 5 étoiles utilise des phrases positives, un avis de 1 ou 2 étoiles des phrases négatives, et un avis de 3 étoiles mélange les deux.

### Catalogue des hôtels

`GET /api/v1/hotels` renvoie les 28 hôtels de la chaîne, avec `hotel_id`, `name`, `city`, `country`, `timezone`, `type` (`urban` ou `resort`) et `rooms`. Il y a des hôtels en Colombie (10), au Mexique (6), au Brésil (6), au Portugal (3) et en Espagne (3). `HP-PT-001` et `HP-PT-002` sont les deux hôtels de [l'historique F1](./f1-hotel-booking-demand.mdx). Les autres sources simulées réutilisent les mêmes codes.

## Génération des données

Les avis sont synthétiques : ils ne sont extraits d'aucune plateforme réelle. Un script de seed les génère avec ces propriétés :

- **Reproductible.** Chaque jour est généré à partir d'une graine fixe, donc une nouvelle exécution produit exactement les mêmes avis.
- **Idempotent.** Les avis ne sont insérés que s'ils n'existent pas encore, donc une deuxième exécution n'insère rien.
- **Volume configurable.** Le mode `dev` génère 30 jours avec environ 20 avis par jour. Le mode `full` génère 365 jours avec environ 300 avis par jour, avec une variation quotidienne de ±15 %.
- **Défauts configurables.** La part d'avis dupliqués est un paramètre, 5 % par défaut.

Le seed peut aussi s'exécuter pour une seule journée, c'est ainsi que le lot quotidien ajoute de nouveaux avis : `python -m src.seed --date 2026-10-01`.

## Utilisation

- **Note de réputation.** La note de réputation de chaque hôtel est la moyenne pondérée de ses avis des 90 derniers jours, les avis des 30 derniers jours comptant double.
- **Page de réputation dans Power BI.** Les avis alimentent la page de réputation du tableau de bord, où l'on peut aussi analyser les thèmes récurrents des textes.
- **Données personnelles.** `reviewer_name` est une donnée personnelle. La couche d'ingestion doit la pseudonymiser avant qu'elle n'atteigne la couche analytique.

<AccessNote icon="alert" title="Problèmes de qualité de données connus">

- Environ 5 % des avis sont dupliqués sur une deuxième plateforme. La copie a le même hôtel, la même note et le même texte, mais un autre `external_id`, un nom de client légèrement différent (sans accents, en minuscules ou en majuscules, ou avec seulement l'initiale du nom de famille), une heure de publication antérieure et parfois sans le point final. L'ingestion doit détecter ces doublons.
- Un avis peut changer ou disparaître après son chargement, via `PATCH` ou `DELETE`. `updated_at` indique quand un avis a changé pour la dernière fois.

</AccessNote>

## L'exécuter en local

Avec Docker installé, clonez le dépôt et lancez l'API, la base de données et le seed avec une seule commande :

```bash
git clone https://github.com/HospedaPlus/api-reviews.git
cd api-reviews
docker compose up --build
```

L'API démarre sur `http://localhost:8000/docs` avec 30 jours d'avis d'exemple. Pour charger une année complète, exécutez `docker compose run --rm seed python -m src.seed --mode full`.

<Note>

L'API est construite avec Python 3.12, FastAPI, SQLModel, Alembic et PostgreSQL 16. Chaque merge sur `main` lance les tests et déploie une nouvelle image sur AWS ECS Fargate.

</Note>
