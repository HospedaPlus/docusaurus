# CI/CD de chaque dépôt

Tous les dépôts HospedaPlus utilisent **GitHub Actions**. L'idée est la même partout :

1. **CI (intégration continue)** s'exécute à chaque Pull Request : elle vérifie le style, lance les tests et construit l'image Docker *sans la publier*. Si quelque chose échoue, la PR affiche un ❌ rouge et n'est pas fusionnée.
2. **CD (livraison/déploiement continu)** s'exécute quand le changement arrive sur `main` : elle publie une **image versionnée** et la **déploie** sur AWS.
3. Le déploiement est **désactivé tant que ses secrets n'existent pas** : s'il manque un secret, le job se termine en vert avec un avis (`Deploy skipped`) au lieu d'échouer.

### Mots utilisés sur cette page

| Terme | Signification |
| --- | --- |
| **Workflow** | Un fichier YAML dans `.github/workflows/`. GitHub l'exécute quand son événement `on:` se produit. |
| **Job** | Un groupe d'étapes qui s'exécute sur une machine Linux neuve (`runs-on: ubuntu-latest`). Les jobs tournent en parallèle sauf si l'un indique `needs:`. |
| **GHCR** | GitHub Container Registry, `ghcr.io/hospedaplus/<repo>` : là où sont stockées les images, à côté du code. |
| **Secret** | Une valeur stockée chiffrée dans *Settings → Secrets and variables → Actions* (clé SSH, hôte). Elle n'apparaît jamais dans les logs. |
| **Environment `production`** | Un environnement GitHub : il regroupe les secrets du déploiement et affiche l'historique des déploiements. |

## 1. hospedaplus-pipeline (CI/CD II : ingénierie des données)

Un seul fichier, `.github/workflows/ci-cd.yml`, avec quatre jobs enchaînés par `needs:` : **lint → test → image → deploy**.

```yaml title=".github/workflows/ci-cd.yml (déclencheurs)"
on:
  pull_request:
    branches: [main]      # every PR: lint + tests + image build (not published)
  push:
    branches: [main]      # merge: the same, then publish and deploy
    tags: ["v*"]          # tag v1.2.3: the image also gets the version as tag
  workflow_dispatch:      # "Run workflow" button

concurrency:
  group: ci-cd-${{ github.ref }}
  cancel-in-progress: true   # a new push cancels the old run of the same branch
```

**Lint** vérifie le style Python avec ruff et que les trois fichiers Compose sont valides (une faute de YAML échoue ici, pas sur le serveur) :

```yaml
  lint:
    steps:
      - uses: astral-sh/ruff-action@v3
        with:
          version: "0.14.3"
          args: check dags spark_jobs tests
      - name: Compose files are valid
        run: |
          cp .env.example .env
          docker compose -f docker-compose.yaml config -q
          docker compose -f docker-compose.nucleo.yaml config -q
          docker compose -f docker-compose.workers.yaml config -q
```

**Test** installe Airflow exactement comme l'image Docker et lance pytest : chaque DAG doit s'importer sans erreur (DagBag), les jobs Spark tournent sur de petites données d'exemple et les contrôles de qualité de `spark_jobs/quality.py` sont testés. Java 17 est installé car Spark en a besoin.

```yaml
  test:
    env:
      AIRFLOW_HOME: ${{ github.workspace }}/.airflow-ci
    steps:
      - uses: actions/setup-python@v5
        with: {python-version: "3.12"}
      - uses: actions/setup-java@v4
        with: {distribution: temurin, java-version: "17"}
      - uses: astral-sh/setup-uv@v6
        with: {activate-environment: true}
      - name: Install Airflow + requirements (same pins as the image)
        run: scripts/ci-install.sh pytest==8.4.2
      - name: DAG validation, Spark jobs and data quality tests
        run: python -m pytest -v -p no:logging
```

`scripts/ci-install.sh` règle un vrai problème : Airflow s'installe avec son fichier officiel de *constraints*, mais nos versions épinglées dans `requirements.txt` doivent l'emporter. Sans cela, uv passait SQLAlchemy en 2.x et cassait Airflow.

```bash title="scripts/ci-install.sh"
AIRFLOW_VERSION=3.1.5
PY=$(python -c 'import sys; print(f"{sys.version_info.major}.{sys.version_info.minor}")')
curl -fsSL "https://raw.githubusercontent.com/apache/airflow/constraints-${AIRFLOW_VERSION}/constraints-${PY}.txt" \
  -o /tmp/constraints.txt
# Drop from the constraints every package we pin ourselves
names=$(grep -vE '^\s*(#|$)' requirements.txt | sed -E 's/[=<>!~ ].*//' | paste -sd'|')
grep -viE "^(${names}|botocore|s3transfer|py4j)==" /tmp/constraints.txt > /tmp/constraints-ci.txt
uv pip install "apache-airflow==${AIRFLOW_VERSION}" -r requirements.txt -c /tmp/constraints-ci.txt "$@"
```

**Image** construit le Dockerfile et, hors PR, le publie sur GHCR avec trois types de tags : le SHA court du commit (`3f2a1bc`), la branche (`main`) et la version (`1.2.3` quand un tag `v1.2.3` est poussé). Le cache de build vit dans GitHub Actions (`type=gha`), donc un build où seuls les DAGs ont changé prend quelques secondes.

```yaml
  image:
    needs: [lint, test]
    permissions: {contents: read, packages: write}
    steps:
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha,prefix=,format=short
            type=ref,event=branch
            type=semver,pattern={{version}}
      - uses: docker/build-push-action@v6
        with:
          push: ${{ github.event_name != 'pull_request' }}   # PRs only build
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

**Deploy** se connecte en SSH aux deux EC2. D'abord le **cœur** (Airflow + RabbitMQ), puis les **workers**, pour que les workers trouvent toujours le nouveau scheduler. Chaque machine fait un pull de `main` et ne recrée que les conteneurs qui ont changé.

```yaml
  deploy:
    needs: image
    if: github.event_name != 'pull_request'
    environment: production
    env:
      SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
      NUCLEO_HOST: ${{ secrets.NUCLEO_HOST }}
      WORKERS_HOST: ${{ secrets.WORKERS_HOST }}
      SSH_USER: ${{ secrets.DEPLOY_SSH_USER || 'ubuntu' }}
    steps:
      - name: Deploy is off until the secrets exist
        id: gate
        run: |
          if [ -z "$SSH_KEY" ] || [ -z "$NUCLEO_HOST" ] || [ -z "$WORKERS_HOST" ]; then
            echo "::notice::Deploy skipped: add DEPLOY_SSH_KEY, NUCLEO_HOST and WORKERS_HOST to turn it on."
            echo "enabled=false" >> "$GITHUB_OUTPUT"
          else
            echo "enabled=true" >> "$GITHUB_OUTPUT"
          fi
      - if: steps.gate.outputs.enabled == 'true'
        name: Núcleo (Airflow + RabbitMQ), then workers
        run: |
          run() { ssh -i ~/.ssh/deploy -o StrictHostKeyChecking=accept-new "$SSH_USER@$1" "$2"; }
          run "$NUCLEO_HOST"  'cd ~/hospedaplus-pipeline && git pull --ff-only && docker compose -f docker-compose.nucleo.yaml up -d --build'
          run "$WORKERS_HOST" 'cd ~/hospedaplus-pipeline && git pull --ff-only && docker compose -f docker-compose.workers.yaml up -d --build && docker compose -f docker-compose.workers.yaml restart'
```

## 2. buenavista-streaming (F2), db_simulated (F3) et hospedaplus-csv (F4) : CI/CD I

Les trois simulateurs de sources partagent le même `cd.yml` (lint → image → déploiement sur l'**EC2 sources**). F2 et F3 ont aussi un `ci.yml` qui lance leurs tests.

### buenavista-streaming (F2 Kafka)

```yaml title=".github/workflows/ci.yml"
on:
  pull_request:
  push:
    branches: [main, develop]
jobs:
  test:
    steps:
      - uses: actions/setup-python@v5
        with: {python-version: "3.12", cache: pip}
      - run: python -m pip install -e ".[dev]"
      - run: ruff check .             # lint
      - run: ruff format --check .    # formatting
      - run: pytest                   # events, Kafka producer/consumer, Neon sinks
```

```yaml title=".github/workflows/cd.yml (étape de déploiement)"
      - if: steps.gate.outputs.enabled == 'true'
        name: Update the EC2 sources
        run: |
          ssh -i ~/.ssh/deploy "$SSH_USER@$HOST" \
            'cd ~/buenavista-streaming && git pull --ff-only && docker compose up -d --build'
```

`docker compose up -d --build` recrée `producer` et `neon-consumer` avec le nouveau code ; Kafka continue de tourner et garde ses données (volume `kafka_data`), donc aucun événement n'est perdu pendant le déploiement.

### db_simulated (F3 moteur de réservation)

La CI démarre un **PostgreSQL 16** jetable à côté du job, les tests tournent donc sur une vraie base : `reservar()`, 50 acheteurs simultanés pour la dernière chambre, pénalités, etc.

```yaml title=".github/workflows/ci.yml"
jobs:
  test:
    services:
      postgres:
        image: postgres:16-alpine
        env: {POSTGRES_USER: hospedaplus, POSTGRES_PASSWORD: hospedaplus, POSTGRES_DB: hospedaplus_test}
        ports: ["5432:5432"]
        options: --health-cmd "pg_isready -U hospedaplus" --health-interval 5s --health-retries 10
    env:
      TEST_DATABASE_URL: postgresql://hospedaplus:hospedaplus@localhost:5432/hospedaplus_test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: "3.12"}
      - run: pip install -e ".[test]"
      - run: pytest -v
```

Le déploiement est plus malin qu'un simple redémarrage : il compare le commit avant et après le `git pull` et ne touche Neon que si le SQL ou les événements locaux ont changé.

```bash title="cd.yml : ce qui s'exécute sur l'EC2 sources"
cd ~/db_simulated && OLD=$(git rev-parse HEAD) && git pull --ff-only
if ! git diff --quiet "$OLD" HEAD -- sql/; then          # schema/functions changed
  docker compose --profile neon run --rm neon-check init  # applies it (init never deletes data)
fi
docker compose --profile neon up -d --build neon-simulator
if ! git diff --quiet "$OLD" HEAD -- data/local_events.csv; then
  docker compose --profile neon run --rm neon-check events   # reloads F6b local events
fi
```

## 3. api-reviews (F5) : le pipeline le plus complet

`ci.yml` a cinq jobs. Le dernier, **CI passed**, est le seul check obligatoire de la protection de branche : il n'est vert que si tous les autres le sont.

| Job | Ce qu'il garantit |
| --- | --- |
| **Lint and format** | `uv sync --frozen` (versions exactes de `uv.lock`), `ruff check`, `ruff format --check` |
| **Secret scan** | `gitleaks` lit *tout* l'historique git et échoue si un mot de passe ou une clé a déjà été commité |
| **Tests (PostgreSQL)** | Alembic `upgrade → downgrade → upgrade`, `alembic check` (modèles = migrations), pytest avec **couverture ≥ 90 %**, et le seed est idempotent (une seconde exécution insère 0 ligne) et reproductible (même empreinte) |
| **Docker build and smoke test** | Construit l'image, la démarre face à un service PostgreSQL, attend `/health/ready`, lance le seed dans l'image, appelle l'API et vérifie que le conteneur tourne avec l'utilisateur non root `app` |
| **CI passed** | Échoue si l'un des jobs ci-dessus n'a pas réussi |

```yaml title="ci.yml : le seed doit être idempotent et reproductible"
      - name: Seed is idempotent and reproducible
        run: |
          count()  { psql "$DATABASE_URL" -tAc "SELECT count(*) FROM reviews"; }
          digest() { psql "$DATABASE_URL" -tAc "SELECT md5(string_agg(platform || external_id || rating || text, ',' ORDER BY platform, external_id)) FROM reviews"; }
          uv run python -m src.seed --mode dev
          first_count=$(count); first_digest=$(digest)
          uv run python -m src.seed --mode dev
          [ "$(count)" = "$first_count" ] || { echo "::error::Second seed run inserted rows"; exit 1; }
```

`cd.yml` ne démarre **qu'après une CI verte sur `main`** (`workflow_run`) et déploie exactement le commit testé par la CI. Il se connecte à AWS par **OIDC** : GitHub obtient un jeton temporaire pour un rôle IAM, donc aucune clé d'accès AWS n'est stockée nulle part.

```yaml title=".github/workflows/cd.yml"
on:
  workflow_run:
    workflows: [CI]
    types: [completed]
    branches: [main]
permissions:
  id-token: write                 # GitHub OIDC -> AWS IAM role
jobs:
  deploy:
    if: vars.AWS_ROLE_ARN != '' && github.event.workflow_run.conclusion == 'success'
    env:
      IMAGE_TAG: ${{ github.event.workflow_run.head_sha || github.sha }}
    steps:
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}
          aws-region: ${{ vars.AWS_REGION }}
      - id: ecr
        uses: aws-actions/amazon-ecr-login@v2
      - uses: docker/build-push-action@v7
        with:
          push: true
          tags: ${{ steps.ecr.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${{ env.IMAGE_TAG }}
      - run: envsubst < deploy/ecs/task-definition.json > task-definition.rendered.json
      - id: render
        uses: aws-actions/amazon-ecs-render-task-definition@v1
        with:
          task-definition: task-definition.rendered.json
          container-name: api
          image: ${{ steps.ecr.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${{ env.IMAGE_TAG }}
      - uses: aws-actions/amazon-ecs-deploy-task-definition@v2
        with:
          task-definition: ${{ steps.render.outputs.task-definition }}
          cluster: ${{ env.ECS_CLUSTER }}
          service: ${{ env.ECS_SERVICE }}
          wait-for-service-stability: true    # fails if the new task does not become healthy
```

L'URL de la base n'est pas non plus dans le dépôt : la task definition pointe vers un ARN **Secrets Manager** (`DATABASE_URL_SECRET_ARN`) et ECS l'injecte au démarrage du conteneur.

## 4. docusaurus (ce site)

```yaml title=".github/workflows/deploy.yml"
on:
  push: {branches: [main]}
  pull_request: {branches: [main]}
jobs:
  build:
    steps:
      - run: npm ci
      - run: npm run typecheck     # TypeScript of the React components
      - run: npm run build         # prebuild generates the docs-chat index, then 5 languages
      - if: github.event_name != 'pull_request'
        uses: actions/upload-pages-artifact@v3
        with: {path: build}
  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'
    permissions: {pages: write, id-token: write}
    steps:
      - uses: actions/deploy-pages@v4
```

Si le job **Deploy** échoue par timeout, c'est GitHub Pages qui est lent, pas le site : ouvrez l'exécution et cliquez sur **Re-run failed jobs**.

## Comment activer les déploiements

1. Ouvrez le port 22 du security group de l'EC2 à GitHub Actions (leurs IP changent, donc dans ce projet il est ouvert à `0.0.0.0/0` avec connexion par clé uniquement).
2. Dans chaque dépôt : **Settings → Secrets and variables → Actions → New repository secret**. Pipeline : `DEPLOY_SSH_KEY`, `NUCLEO_HOST`, `WORKERS_HOST`. Sources : `DEPLOY_SSH_KEY`, `SOURCES_HOST`. api-reviews utilise plutôt des *variables* du dépôt (`AWS_ROLE_ARN`, `AWS_REGION`, `ECR_REPOSITORY`, `ECS_CLUSTER`, `ECS_SERVICE`, …).
3. Poussez sur `main` (ou cliquez sur **Run workflow**). L'exécution affiche `Deploy` en vert et le log de l'étape montre la sortie `docker compose` du serveur.

**Comment vérifier une exécution :** onglet **Actions** du dépôt → cliquez sur l'exécution → chaque job affiche ses étapes ; une étape avec un ❌ rouge contient l'erreur exacte. Une PR ne peut être fusionnée que lorsque ses checks sont verts.
