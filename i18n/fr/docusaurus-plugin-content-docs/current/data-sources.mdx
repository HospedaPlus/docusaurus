# Sources de données

HospedaPlus Revenue intègre sept sources de données, de F1 à F7. F1, F6 et F7 sont des données publiques réelles. F2 à F5 sont **simulées** : l'équipe a construit un générateur pour chacune, il tourne en permanence sur AWS et produit des données à la fréquence et au volume demandés par le projet.

## Où chaque source est stockée d'abord

```text
Simulateurs sur AWS                         Stockée d'abord dans               Lac (S3)
Producteur F2 ─► Kafka ─► consommateur ────► Neon · streaming + operation ─┐
Seed + simulateur F3 ──────────────────────► Neon · operation ─────────────┤ Airflow, toutes les heures
CSV des événements locaux F6 ──────────────► Neon · operation.local_events ┤ et chaque nuit
Générateur hebdomadaire F4 ─┬─ reservar() ─► Neon · operation ─────────────┤
                            └─ fichiers bruts ──────────────────────────────┼─► S3 bronze ─► silver ─► gold
API d'avis F5 ─────────────────────────────► PostgreSQL de l'API ─ Airflow ┤
CSV F1, API jours fériés F6, API change F7 ── Airflow ──────────────────────┘
```

- **D'abord dans Neon (F2, F3, événements F6, réservations F4).** Ce sont des données opérationnelles : chaque réservation, quel que soit son canal, passe par la même fonction `operation.reservar()`, donc tous les canaux partagent un seul inventaire et il n'y a jamais de surréservation. Le pipeline lit Neon avec un rôle en lecture seule et copie les changements vers S3 toutes les heures, plus un instantané complet chaque nuit.
- **D'abord dans S3 (F1, fichiers F4, jours fériés F6, F7).** Ce sont des fichiers ou des API publiques sans rien à opérer, donc ils vont dans `s3://…/bronze/` tels qu'ils arrivent, sans modification.
- **F5** garde ses avis dans la base propre à l'API, comme le ferait une vraie plateforme ; le pipeline lit l'API toutes les heures.

<Note>
  **Seed de données.** Toutes les données des sources simulées sont générées par du code versionné dans chaque dépôt. Les générateurs utilisent une graine aléatoire fixe pour que les données soient reproductibles, sont idempotents, permettent de choisir le volume (petit mode de développement ou mode complet), gardent l'intégrité référentielle grâce à un seul catalogue partagé (les mêmes codes d'hôtel, de type de chambre, de canal et de client partout), injectent les problèmes de qualité connus à un taux configurable et tournent aussi bien en local avec Docker que sur AWS.
</Note>

<AccessNote icon="alert" title="Problèmes de qualité de données connus">

Les données arrivent avec les défauts suivants, et les sources simulées les injectent volontairement :

- F1 contient `"NULL"` sous forme de texte dans les champs agent et company, et des valeurs d'ADR négatives ou extrêmes.
- Des réservations avec zéro adulte, zéro enfant et zéro bébé (F1, F3).
- Des dates de départ antérieures à la date d'arrivée (F3).
- Des devises manquantes dans les fichiers des agences (F4, ~10 %).
- Des réservations en double entre canaux avec de légères différences dans le nom du client (F4, ~10 %), et des avis en double entre plateformes (F5, ~5 %).
- Des événements de modification qui arrivent avant l'événement de création (F2, ~5 %).

</AccessNote>
