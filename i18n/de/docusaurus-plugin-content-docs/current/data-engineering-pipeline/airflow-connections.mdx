# Airflow-Verbindungen und wie sie genutzt werden

Ein DAG ist nur nützlich, wenn seine Tasks die umgebenden Systeme erreichen: Neon, S3, die Quell-APIs sowie Broker und Datenbank von Airflow selbst. Diese Seite zeigt **jede Verbindung der Pipeline, wo sie definiert ist und den genauen Code, der sie öffnet**.

<ConnectionsFlow />

## Die vier Arten von Verbindungen

| # | Verbindung | Definiert in | Format | Genutzt von |
| --- | --- | --- | --- | --- |
| 1 | Infrastruktur von Airflow: Metadaten-DB, Celery-Broker, Result Backend | `environment:` der Compose-Dateien | SQLAlchemy- / AMQP-URLs | Scheduler, API-Server, Worker |
| 2 | Airflow-**Connection** `aws_default` | Umgebungsvariable `AIRFLOW_CONN_AWS_DEFAULT` (URI) | `aws://?region_name=us-east-2` | Remote-Task-Logs in `s3://…/airflow-logs/` |
| 3 | Task-Verbindungen zu **Neon** | `NEON_READ_URL`, `NEON_WRITE_URL` in `.env` | PostgreSQL-URI | Bronze-DAGs (lesen) und `gold_neon_writeback` (schreiben) |
| 4 | Task-Verbindungen zu **S3** und den **HTTP-APIs** | IAM-Rolle der EC2 + `S3_BUCKET`, `F5_API_URL`, `NAGER_BASE_URL` | Bucket-Name / Basis-URL | Alle bronze-, silver- und gold-Tasks |

## 1. Die eigenen Verbindungen von Airflow (Infrastruktur)

Airflow braucht eine Datenbank für die DAG-Läufe und einen Broker, um Tasks an die Celery-Worker zu senden. Sie werden über Umgebungsvariablen `AIRFLOW__<SEKTION>__<SCHLUESSEL>` gesetzt, die Airflow statt `airflow.cfg` liest:

```yaml title="docker-compose.workers.yaml (die Worker erreichen den Kern über seine private IP)"
# Tasks gehen an Celery-Worker auf einer anderen Maschine
AIRFLOW__CORE__EXECUTOR: CeleryExecutor
# Metadaten-DB (Postgres auf der Kern-EC2)
AIRFLOW__DATABASE__SQL_ALCHEMY_CONN: postgresql+psycopg2://airflow:${POSTGRES_PASSWORD}@${NUCLEO_HOST}:5432/airflow
# Celery-Broker (RabbitMQ auf der Kern-EC2): dort legt der Scheduler die Tasks ab
AIRFLOW__CELERY__BROKER_URL: amqp://${RABBITMQ_USER}:${RABBITMQ_PASSWORD}@${NUCLEO_HOST}:5672//
# dort schreiben die Worker das Ergebnis jedes Tasks hin
AIRFLOW__CELERY__RESULT_BACKEND: db+postgresql://airflow:${POSTGRES_PASSWORD}@${NUCLEO_HOST}:5432/airflow
# Airflow 3: Worker melden den Task-Status an den API-Server
AIRFLOW__CORE__EXECUTION_API_SERVER_URL: 'http://${NUCLEO_HOST}:8080/execution/'
```

**So funktioniert es:** Der Scheduler (Kern) legt eine Nachricht in die RabbitMQ-Queue `bronze`, `silver` oder `gold`; der Worker, der auf diese Queue hört, nimmt sie, führt den Task aus und meldet den Status über die Execution API. Die Ports 5432, 5672 und 8080 des Kerns sind **nur für die Security Group der Worker** offen.

## 2. Die Airflow-Connection `aws_default`

Eine *Airflow Connection* ist ein benannter Satz Zugangsdaten, den Airflow-Hooks über ihre `conn_id` finden. Statt sie von Hand in *Admin → Connections* anzulegen (sie ginge verloren, wenn die Metadaten-DB neu erstellt wird), wird sie als Umgebungsvariable `AIRFLOW_CONN_<CONN_ID>` mit einer URI deklariert:

```yaml title="docker-compose.nucleo.yaml / docker-compose.workers.yaml"
# Definiert die Verbindung aws_default: keine Schlüssel, nur die Region (Zugangsdaten kommen aus der IAM-Rolle)
AIRFLOW_CONN_AWS_DEFAULT: 'aws://?region_name=${AWS_DEFAULT_REGION:-us-east-2}'
# Schaltet Remote-Task-Logs ein
AIRFLOW__LOGGING__REMOTE_LOGGING: 'true'
# S3-Ordner, in den die Logs hochgeladen werden
AIRFLOW__LOGGING__REMOTE_BASE_LOG_FOLDER: s3://${S3_BUCKET}/airflow-logs
# Verbindung zum Hochladen: die oben definierte
AIRFLOW__LOGGING__REMOTE_LOG_CONN_ID: aws_default
```

Die URI enthält **keinen Access Key**: Findet der Amazon-Provider keinen Schlüssel, nutzt boto3 die **IAM-Rolle der EC2** (`hospedaplus-pipeline-role`) und erhält temporäre Zugangsdaten. Sie dient den Logs: Ein Task läuft auf der Worker-EC2, sein Log wird nach S3 hochgeladen, und die UI auf dem Kern liest es von dort.

```bash title="Prüfen aus einem beliebigen Airflow-Container"
# Zeigt die Verbindung aws_default so, wie Airflow sie sieht
docker compose -f docker-compose.nucleo.yaml exec airflow-scheduler airflow connections get aws_default
# Fragt AWS, wer wir sind: zeigt die verwendete IAM-Rolle
docker compose -f docker-compose.nucleo.yaml exec airflow-scheduler \
  python -c "import boto3; print(boto3.client('sts').get_caller_identity()['Arn'])"
```

## 3. Neon: Umgebungsvariable + psycopg2

Die DAGs nutzen für Neon keinen Airflow-Hook. Der Connection-String steht in der `.env` der Worker, und das gemeinsame Modul `dags/hospedaplus/lake.py` liest ihn; ist er leer, schlägt der Task absichtlich mit einer klaren Meldung fehl.

```python title="dags/hospedaplus/lake.py"
# Gibt den Neon-Connection-String zurück
def neon_url() -> str:
    # Liest ihn aus der Umgebung (.env der Worker)
    url = os.getenv("NEON_READ_URL", "")
    # Fehlt er...
    if not url:
        # ...mit klarer Meldung fehlschlagen statt mit einem kryptischen Verbindungsfehler
        raise RuntimeError("NEON_READ_URL is empty: set it in .env (role etl_reader)")
    # Sonst zurückgeben
    return url
```

```python title="dags/hospedaplus/neon.py: jeder Lesevorgang liefert JSON Lines"
# Führt eine Abfrage aus und gibt (JSON-Lines-Bytes, Zeilenzahl) zurück
def dump(sql: str, params: tuple = ()) -> tuple[bytes, int]:
    # Öffnet Verbindung und Cursor; beide werden am Blockende geschlossen
    with psycopg2.connect(neon_url()) as conn, conn.cursor() as cur:
        # Führt die Abfrage mit ihren Parametern aus (nie in den Text geklebt: keine SQL-Injection)
        cur.execute(sql, params)
        # Spaltennamen des Ergebnisses
        cols = [c.name for c in cur.description]
        # Alle Zeilen
        rows = cur.fetchall()
    # Macht aus jeder Zeile eine JSON-Zeile {Spalte: Wert}
    lines = [json.dumps(dict(zip(cols, r)), default=str, ensure_ascii=False) for r in rows]
    # Verbindet die Zeilen, kodiert sie als Bytes und gibt sie mit der Zeilenzahl zurück
    return ("\n".join(lines) + ("\n" if lines else "")).encode(), len(rows)
```

Nur ein Task schreibt nach Neon, mit anderer Rolle und Variable:

```python title="dags/gold_neon_writeback.py"
# Schreib-URL: Rolle app_writer
url = os.getenv("NEON_WRITE_URL", "")
# Eine Transaktion: alle Zeilen oder keine
with psycopg2.connect(url) as conn, conn.cursor() as cur:
    # Führt das UPSERT einmal pro Zeile aus
    cur.executemany(UPSERT, rows)
```

```bash title=".env der Worker-EC2 (Platzhalter: echte Werte nie committen)"
# Nur-Lese-Rolle für die Bronze-Extrakte
NEON_READ_URL=postgresql://etl_reader:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech/hospedaplus?sslmode=require
# Schreibrolle für gold_neon_writeback
NEON_WRITE_URL=postgresql://app_writer:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech/hospedaplus?sslmode=require
```

## 4. S3 und die HTTP-APIs

**S3 mit boto3.** Weder im Code noch in `.env` steht ein Schlüssel: `boto3.client("s3")` findet die IAM-Rolle der EC2 selbst. `S3_ENDPOINT_URL` ist auf AWS leer und wird nur für lokale Tests mit MinIO gesetzt.

```python title="dags/hospedaplus/lake.py"
# Bucket-Name aus .env (Standardwert, falls er fehlt)
BUCKET = os.getenv("S3_BUCKET", "hospedaplus-lakehouse")

# Erstellt den S3-Client
def s3_client():
    # Keine Schlüssel: boto3 findet die IAM-Rolle; Endpoint nur für MinIO-Tests
    return boto3.client("s3", endpoint_url=os.getenv("S3_ENDPOINT_URL") or None)

# Schreibt eine Datei nach S3 und gibt ihre Adresse zurück
def put(key: str, body: bytes, content_type: str = "application/json") -> str:
    # Lädt die Bytes nach bucket/key (überschreibt, falls vorhanden)
    s3_client().put_object(Bucket=BUCKET, Key=key, Body=body, ContentType=content_type)
    # Gibt die vollständige s3://-Adresse zurück
    return f"s3://{BUCKET}/{key}"
```

**S3 mit Spark.** Spark nutzt das Protokoll `s3a://` (Jars `hadoop-aws` + `aws-java-sdk-bundle` im Image) und dieselbe IAM-Rolle über `DefaultAWSCredentialsProviderChain`:

```python title="spark_jobs/session.py"
# Spark-Session mit Namen, auf allen CPU-Kernen des Workers
SparkSession.builder.appName(app).master("local[*]")
    # Fügt die Jars von hadoop-aws und AWS-SDK hinzu
    .config("spark.jars", jars)
    # Nutzt das S3A-Dateisystem für s3a://-Adressen
    .config("spark.hadoop.fs.s3a.impl", "org.apache.hadoop.fs.s3a.S3AFileSystem")
    # Zugangsdaten: die Standard-AWS-Kette (findet die IAM-Rolle der EC2)
    .config("spark.hadoop.fs.s3a.aws.credentials.provider",
            "com.amazonaws.auth.DefaultAWSCredentialsProviderChain")

# Baut die Adresse einer Tabelle im Lake
def path(layer: str, name: str) -> str:
    # z. B. s3a://bucket/silver/reservas
    return f"s3a://{os.getenv('S3_BUCKET')}/{layer}/{name}"
```

**HTTP-APIs mit requests.** Die Basis-URL kommt aus `.env`, der optionale API-Key geht in einen Header:

```python title="dags/bronze_f5_reviews.py"
# API-Adresse aus .env, ohne Schrägstrich am Ende
base = os.getenv("F5_API_URL", "").rstrip("/")
# Schickt den API-Key nur im Header, wenn er konfiguriert ist
headers = {"x-api-key": os.environ["F5_API_KEY"]} if os.getenv("F5_API_KEY") else {}
# Fragt die seit Beginn dieses Laufs geänderten Bewertungen ab, Seite für Seite
r = requests.get(f"{base}/api/v1/reviews", headers=headers, timeout=60,
                 params={"updated_from": data_interval_start.isoformat(), "page": page, "page_size": 100})
```

## Warum Umgebungsvariablen statt Hooks für Neon und S3

| Grund | Detail |
| --- | --- |
| Ein Ort für alles | Dieselbe `.env` konfiguriert Airflow, die DAGs und die Spark-Jobs; Spark-Jobs laufen ohnehin außerhalb der Airflow-Hooks. |
| Übersteht einen Neuaufbau | In der Metadaten-DB ist nichts gespeichert, ein neu erstelltes Postgres verliert also keine Verbindung. |
| Gleicher Code in der CI | Die Tests führen den DAG-Code mit Fake-Variablen aus, ohne Airflow-UI. |
| Überhaupt keine AWS-Keys | Der S3-Zugriff kommt aus der IAM-Rolle; es gibt nichts zu rotieren oder zu leaken. |

## Dasselbe mit Airflow-Hooks (optional)

Die Amazon- und Postgres-Provider sind bereits installiert (`apache-airflow-providers-amazon==9.16.0`, `apache-airflow-providers-postgres==6.4.0`), das Projekt kann also ohne Image-Änderung auf Hooks umsteigen. Die Verbindung als URI deklarieren:

```bash title=".env (Beispiel, Platzhalter)"
# AIRFLOW_CONN_<ID> erzeugt die Verbindung neon_reader aus einer URI
AIRFLOW_CONN_NEON_READER='postgresql://etl_reader:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech:5432/hospedaplus?sslmode=require'
```

```python title="Ein Task, der die Hooks nutzt"
# Airflow-Hook für PostgreSQL
from airflow.providers.postgres.hooks.postgres import PostgresHook
# Airflow-Hook für S3
from airflow.providers.amazon.aws.hooks.s3 import S3Hook

# Task, der auf einem Bronze-Worker läuft
@task(queue="bronze")
def copy_hotels():
    # Liest alle Hotels über die Verbindung neon_reader
    rows = PostgresHook(postgres_conn_id="neon_reader").get_records("SELECT * FROM operation.hotels")
    # Eine JSON-Zeile pro Zeile
    body = "\n".join(json.dumps(r, default=str) for r in rows)
    # Lädt den Text über die Verbindung aws_default nach S3
    S3Hook(aws_conn_id="aws_default").load_string(body, key="bronze/neon_dims/hotels/test.jsonl",
                                                  bucket_name="hospedaplus-lakehouse-buenavista", replace=True)
```

Beide Ansätze öffnen dieselben Verbindungen; das Projekt nutzt aus den oben genannten Gründen Umgebungsvariablen.

## DAGs miteinander verbinden: Assets

DAGs sind auch untereinander „verbunden“, ohne feste Uhrzeiten, über **Assets** (Airflow 3). Ein Task deklariert mit `outlets=`, was er schreibt, und ein DAG deklariert mit `schedule=`, worauf er wartet:

```python title="dags/hospedaplus/lake.py + dags/silver_reservas_daily.py"
# Ein Asset ist ein Name für einen Ordner des Lakes
BRONZE_F3_RESERVATIONS = Asset("s3://hospedaplus-lakehouse/bronze/f3_reservations")

# bronze: "Ich habe das aktualisiert" (outlets markiert das Asset als geändert, wenn der Task erfolgreich endet)
@task(queue="bronze", outlets=[BRONZE_F3_RESERVATIONS])
def f3_reservations(...): ...

# silver: läuft, wenn sich seine Eingaben ändern (& = alle, | = irgendeine)
@dag(schedule=((SILVER_FX_DAILY & BRONZE_F3_FULL & BRONZE_NEON_DIMS) | BRONZE_F3_RESERVATIONS))
def silver_reservas_daily(): ...
```

`&` wartet auf alle Assets, `|` läuft, sobald sich eines ändert. Siehe [DAGs](./dags.mdx) und [Verbindung zu Neon und S3](./how-to-connect.mdx).
