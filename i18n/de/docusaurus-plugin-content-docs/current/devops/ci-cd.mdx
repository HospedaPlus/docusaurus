# CI/CD jedes Repositorys

Alle HospedaPlus-Repositorys nutzen **GitHub Actions**. Die Idee ist überall dieselbe:

1. **CI (Continuous Integration)** läuft bei jedem Pull Request: prüft den Stil, führt die Tests aus und baut das Docker-Image, *ohne es zu veröffentlichen*. Schlägt etwas fehl, zeigt der PR ein rotes ❌ und wird nicht gemergt.
2. **CD (Continuous Delivery/Deployment)** läuft, wenn die Änderung `main` erreicht: veröffentlicht ein **versioniertes Image** und **deployt** es auf AWS.
3. Das Deployment ist **aus, bis seine Secrets existieren**: Fehlt ein Secret, endet der Job grün mit einem Hinweis (`Deploy skipped`), statt fehlzuschlagen.

### Begriffe auf dieser Seite

| Begriff | Bedeutung |
| --- | --- |
| **Workflow** | Eine YAML-Datei in `.github/workflows/`. GitHub führt sie aus, wenn ihr `on:`-Ereignis eintritt. |
| **Job** | Eine Gruppe von Schritten auf einer frischen Linux-Maschine (`runs-on: ubuntu-latest`). Jobs laufen parallel, außer einer sagt `needs:`. |
| **GHCR** | GitHub Container Registry, `ghcr.io/hospedaplus/<repo>`: dort liegen die Images, direkt neben dem Code. |
| **Secret** | Ein verschlüsselt gespeicherter Wert in *Settings → Secrets and variables → Actions* (SSH-Key, Host). Er erscheint nie in den Logs. |
| **Environment `production`** | Eine GitHub-Umgebung: bündelt die Deployment-Secrets und zeigt die Deployment-Historie. |

## 1. hospedaplus-pipeline (CI/CD II: Data Engineering)

Eine Datei, `.github/workflows/ci-cd.yml`, mit vier per `needs:` verketteten Jobs: **lint → test → image → deploy**.

```yaml title=".github/workflows/ci-cd.yml (Auslöser)"
on:
  pull_request:
    branches: [main]      # every PR: lint + tests + image build (not published)
  push:
    branches: [main]      # merge: the same, then publish and deploy
    tags: ["v*"]          # tag v1.2.3: the image also gets the version as tag
  workflow_dispatch:      # "Run workflow" button

concurrency:
  group: ci-cd-${{ github.ref }}
  cancel-in-progress: true   # a new push cancels the old run of the same branch
```

**Lint** prüft den Python-Stil mit ruff und ob die drei Compose-Dateien gültig sind (ein YAML-Tippfehler scheitert hier, nicht auf dem Server):

```yaml
  lint:
    steps:
      - uses: astral-sh/ruff-action@v3
        with:
          version: "0.14.3"
          args: check dags spark_jobs tests
      - name: Compose files are valid
        run: |
          cp .env.example .env
          docker compose -f docker-compose.yaml config -q
          docker compose -f docker-compose.nucleo.yaml config -q
          docker compose -f docker-compose.workers.yaml config -q
```

**Test** installiert Airflow genau wie das Docker-Image und führt pytest aus: Jeder DAG muss sich fehlerfrei importieren lassen (DagBag), die Spark-Jobs laufen mit kleinen Beispieldaten, und die Qualitätsprüfungen aus `spark_jobs/quality.py` werden getestet. Java 17 wird installiert, weil Spark es braucht.

```yaml
  test:
    env:
      AIRFLOW_HOME: ${{ github.workspace }}/.airflow-ci
    steps:
      - uses: actions/setup-python@v5
        with: {python-version: "3.12"}
      - uses: actions/setup-java@v4
        with: {distribution: temurin, java-version: "17"}
      - uses: astral-sh/setup-uv@v6
        with: {activate-environment: true}
      - name: Install Airflow + requirements (same pins as the image)
        run: scripts/ci-install.sh pytest==8.4.2
      - name: DAG validation, Spark jobs and data quality tests
        run: python -m pytest -v -p no:logging
```

`scripts/ci-install.sh` löst ein echtes Problem: Airflow wird mit seiner offiziellen *Constraints*-Datei installiert, aber unsere eigenen Pins in `requirements.txt` müssen gewinnen. Ohne das hob uv SQLAlchemy auf 2.x und Airflow ging kaputt.

```bash title="scripts/ci-install.sh"
AIRFLOW_VERSION=3.1.5
PY=$(python -c 'import sys; print(f"{sys.version_info.major}.{sys.version_info.minor}")')
curl -fsSL "https://raw.githubusercontent.com/apache/airflow/constraints-${AIRFLOW_VERSION}/constraints-${PY}.txt" \
  -o /tmp/constraints.txt
# Drop from the constraints every package we pin ourselves
names=$(grep -vE '^\s*(#|$)' requirements.txt | sed -E 's/[=<>!~ ].*//' | paste -sd'|')
grep -viE "^(${names}|botocore|s3transfer|py4j)==" /tmp/constraints.txt > /tmp/constraints-ci.txt
uv pip install "apache-airflow==${AIRFLOW_VERSION}" -r requirements.txt -c /tmp/constraints-ci.txt "$@"
```

**Image** baut das Dockerfile und veröffentlicht es außerhalb von PRs in GHCR mit drei Tag-Arten: dem kurzen Commit-SHA (`3f2a1bc`), dem Branch (`main`) und der Version (`1.2.3`, wenn ein Tag `v1.2.3` gepusht wird). Der Build-Cache liegt in GitHub Actions (`type=gha`), daher dauert ein Build, bei dem sich nur DAGs geändert haben, Sekunden.

```yaml
  image:
    needs: [lint, test]
    permissions: {contents: read, packages: write}
    steps:
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha,prefix=,format=short
            type=ref,event=branch
            type=semver,pattern={{version}}
      - uses: docker/build-push-action@v6
        with:
          push: ${{ github.event_name != 'pull_request' }}   # PRs only build
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

**Deploy** verbindet sich per SSH mit beiden EC2. Zuerst der **Kern** (Airflow + RabbitMQ), dann die **Worker**, damit die Worker immer den neuen Scheduler vorfinden. Jede Maschine zieht `main` und erstellt nur die geänderten Container neu.

```yaml
  deploy:
    needs: image
    if: github.event_name != 'pull_request'
    environment: production
    env:
      SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
      NUCLEO_HOST: ${{ secrets.NUCLEO_HOST }}
      WORKERS_HOST: ${{ secrets.WORKERS_HOST }}
      SSH_USER: ${{ secrets.DEPLOY_SSH_USER || 'ubuntu' }}
    steps:
      - name: Deploy is off until the secrets exist
        id: gate
        run: |
          if [ -z "$SSH_KEY" ] || [ -z "$NUCLEO_HOST" ] || [ -z "$WORKERS_HOST" ]; then
            echo "::notice::Deploy skipped: add DEPLOY_SSH_KEY, NUCLEO_HOST and WORKERS_HOST to turn it on."
            echo "enabled=false" >> "$GITHUB_OUTPUT"
          else
            echo "enabled=true" >> "$GITHUB_OUTPUT"
          fi
      - if: steps.gate.outputs.enabled == 'true'
        name: Núcleo (Airflow + RabbitMQ), then workers
        run: |
          run() { ssh -i ~/.ssh/deploy -o StrictHostKeyChecking=accept-new "$SSH_USER@$1" "$2"; }
          run "$NUCLEO_HOST"  'cd ~/hospedaplus-pipeline && git pull --ff-only && docker compose -f docker-compose.nucleo.yaml up -d --build'
          run "$WORKERS_HOST" 'cd ~/hospedaplus-pipeline && git pull --ff-only && docker compose -f docker-compose.workers.yaml up -d --build && docker compose -f docker-compose.workers.yaml restart'
```

## 2. buenavista-streaming (F2), db_simulated (F3) und hospedaplus-csv (F4): CI/CD I

Die drei Quellsimulatoren teilen dasselbe `cd.yml` (lint → image → Deployment auf die **EC2 Quellen**). F2 und F3 haben zusätzlich ein `ci.yml`, das ihre Tests ausführt.

### buenavista-streaming (F2 Kafka)

```yaml title=".github/workflows/ci.yml"
on:
  pull_request:
  push:
    branches: [main, develop]
jobs:
  test:
    steps:
      - uses: actions/setup-python@v5
        with: {python-version: "3.12", cache: pip}
      - run: python -m pip install -e ".[dev]"
      - run: ruff check .             # lint
      - run: ruff format --check .    # formatting
      - run: pytest                   # events, Kafka producer/consumer, Neon sinks
```

```yaml title=".github/workflows/cd.yml (Deploy-Schritt)"
      - if: steps.gate.outputs.enabled == 'true'
        name: Update the EC2 sources
        run: |
          ssh -i ~/.ssh/deploy "$SSH_USER@$HOST" \
            'cd ~/buenavista-streaming && git pull --ff-only && docker compose up -d --build'
```

`docker compose up -d --build` erstellt `producer` und `neon-consumer` mit dem neuen Code neu; Kafka läuft weiter und behält seine Daten (Volume `kafka_data`), sodass beim Deployment kein Event verloren geht.

### db_simulated (F3 Buchungs-Engine)

Die CI startet ein wegwerfbares **PostgreSQL 16** neben dem Job, damit die Tests gegen eine echte Datenbank laufen: `reservar()`, 50 gleichzeitige Käufer für das letzte Zimmer, Strafen usw.

```yaml title=".github/workflows/ci.yml"
jobs:
  test:
    services:
      postgres:
        image: postgres:16-alpine
        env: {POSTGRES_USER: hospedaplus, POSTGRES_PASSWORD: hospedaplus, POSTGRES_DB: hospedaplus_test}
        ports: ["5432:5432"]
        options: --health-cmd "pg_isready -U hospedaplus" --health-interval 5s --health-retries 10
    env:
      TEST_DATABASE_URL: postgresql://hospedaplus:hospedaplus@localhost:5432/hospedaplus_test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: "3.12"}
      - run: pip install -e ".[test]"
      - run: pytest -v
```

Das Deployment ist klüger als ein einfacher Neustart: Es vergleicht den Commit vor und nach `git pull` und fasst Neon nur an, wenn sich SQL oder die lokalen Events geändert haben.

```bash title="cd.yml: was auf der EC2 Quellen läuft"
cd ~/db_simulated && OLD=$(git rev-parse HEAD) && git pull --ff-only
if ! git diff --quiet "$OLD" HEAD -- sql/; then          # schema/functions changed
  docker compose --profile neon run --rm neon-check init  # applies it (init never deletes data)
fi
docker compose --profile neon up -d --build neon-simulator
if ! git diff --quiet "$OLD" HEAD -- data/local_events.csv; then
  docker compose --profile neon run --rm neon-check events   # reloads F6b local events
fi
```

## 3. api-reviews (F5): die vollständigste Pipeline

`ci.yml` hat fünf Jobs. Der letzte, **CI passed**, ist der einzige Pflicht-Check des Branch-Schutzes: Er ist nur grün, wenn alle anderen es sind.

| Job | Was er garantiert |
| --- | --- |
| **Lint and format** | `uv sync --frozen` (exakte Versionen aus `uv.lock`), `ruff check`, `ruff format --check` |
| **Secret scan** | `gitleaks` liest die *gesamte* Git-Historie und schlägt fehl, wenn je ein Passwort oder Schlüssel committet wurde |
| **Tests (PostgreSQL)** | Alembic `upgrade → downgrade → upgrade`, `alembic check` (Modelle = Migrationen), pytest mit **≥ 90 % Abdeckung**, und der Seed ist idempotent (ein zweiter Lauf fügt 0 Zeilen ein) und reproduzierbar (gleicher Digest) |
| **Docker build and smoke test** | Baut das Image, startet es gegen einen PostgreSQL-Service, wartet auf `/health/ready`, führt den Seed im Image aus, ruft die API auf und prüft, dass der Container als Nicht-Root-Benutzer `app` läuft |
| **CI passed** | Schlägt fehl, wenn einer der Jobs oben nicht erfolgreich war |

```yaml title="ci.yml: der Seed muss idempotent und reproduzierbar sein"
      - name: Seed is idempotent and reproducible
        run: |
          count()  { psql "$DATABASE_URL" -tAc "SELECT count(*) FROM reviews"; }
          digest() { psql "$DATABASE_URL" -tAc "SELECT md5(string_agg(platform || external_id || rating || text, ',' ORDER BY platform, external_id)) FROM reviews"; }
          uv run python -m src.seed --mode dev
          first_count=$(count); first_digest=$(digest)
          uv run python -m src.seed --mode dev
          [ "$(count)" = "$first_count" ] || { echo "::error::Second seed run inserted rows"; exit 1; }
```

`cd.yml` startet **erst, nachdem die CI auf `main` grün war** (`workflow_run`), und deployt genau den getesteten Commit. Die Anmeldung bei AWS erfolgt per **OIDC**: GitHub erhält ein temporäres Token für eine IAM-Rolle, daher ist nirgendwo ein AWS Access Key gespeichert.

```yaml title=".github/workflows/cd.yml"
on:
  workflow_run:
    workflows: [CI]
    types: [completed]
    branches: [main]
permissions:
  id-token: write                 # GitHub OIDC -> AWS IAM role
jobs:
  deploy:
    if: vars.AWS_ROLE_ARN != '' && github.event.workflow_run.conclusion == 'success'
    env:
      IMAGE_TAG: ${{ github.event.workflow_run.head_sha || github.sha }}
    steps:
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}
          aws-region: ${{ vars.AWS_REGION }}
      - id: ecr
        uses: aws-actions/amazon-ecr-login@v2
      - uses: docker/build-push-action@v7
        with:
          push: true
          tags: ${{ steps.ecr.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${{ env.IMAGE_TAG }}
      - run: envsubst < deploy/ecs/task-definition.json > task-definition.rendered.json
      - id: render
        uses: aws-actions/amazon-ecs-render-task-definition@v1
        with:
          task-definition: task-definition.rendered.json
          container-name: api
          image: ${{ steps.ecr.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${{ env.IMAGE_TAG }}
      - uses: aws-actions/amazon-ecs-deploy-task-definition@v2
        with:
          task-definition: ${{ steps.render.outputs.task-definition }}
          cluster: ${{ env.ECS_CLUSTER }}
          service: ${{ env.ECS_SERVICE }}
          wait-for-service-stability: true    # fails if the new task does not become healthy
```

Auch die Datenbank-URL steht nicht im Repository: Die Task Definition verweist auf ein **Secrets-Manager**-ARN (`DATABASE_URL_SECRET_ARN`), und ECS injiziert sie beim Start des Containers.

## 4. docusaurus (diese Seite)

```yaml title=".github/workflows/deploy.yml"
on:
  push: {branches: [main]}
  pull_request: {branches: [main]}
jobs:
  build:
    steps:
      - run: npm ci
      - run: npm run typecheck     # TypeScript of the React components
      - run: npm run build         # prebuild generates the docs-chat index, then 5 languages
      - if: github.event_name != 'pull_request'
        uses: actions/upload-pages-artifact@v3
        with: {path: build}
  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'
    permissions: {pages: write, id-token: write}
    steps:
      - uses: actions/deploy-pages@v4
```

Schlägt der Job **Deploy** mit einem Timeout fehl, ist GitHub Pages langsam, nicht die Seite: Lauf öffnen und **Re-run failed jobs** klicken.

## So werden die Deployments aktiviert

1. Port 22 der EC2-Security-Group für GitHub Actions öffnen (deren IPs ändern sich, daher ist er in diesem Projekt für `0.0.0.0/0` offen, Login nur per Schlüssel).
2. In jedem Repository: **Settings → Secrets and variables → Actions → New repository secret**. Pipeline: `DEPLOY_SSH_KEY`, `NUCLEO_HOST`, `WORKERS_HOST`. Quellen: `DEPLOY_SSH_KEY`, `SOURCES_HOST`. api-reviews nutzt stattdessen Repository-*Variablen* (`AWS_ROLE_ARN`, `AWS_REGION`, `ECR_REPOSITORY`, `ECS_CLUSTER`, `ECS_SERVICE`, …).
3. Auf `main` pushen (oder **Run workflow** klicken). Der Lauf zeigt `Deploy` in Grün, und das Schritt-Log zeigt die `docker compose`-Ausgabe des Servers.

**Einen Lauf prüfen:** Tab **Actions** des Repositorys → Lauf anklicken → jeder Job zeigt seine Schritte; ein Schritt mit rotem ❌ enthält den genauen Fehler. Ein PR kann nur gemergt werden, wenn seine Checks grün sind.
