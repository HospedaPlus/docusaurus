# Conexiones de Airflow y cómo se usan

Un DAG solo sirve si sus tareas pueden llegar a los sistemas que lo rodean: Neon, S3, las APIs de las fuentes y el broker y la base de datos del propio Airflow. Esta página muestra **cada conexión que usa el pipeline, dónde se define y el código exacto que la abre**.

<ConnectionsFlow />

## Los cuatro tipos de conexión

| # | Conexión | Se define en | Formato | La usa |
| --- | --- | --- | --- | --- |
| 1 | Infraestructura del propio Airflow: base de metadatos, broker de Celery, result backend | `environment:` de los archivos Compose | URLs SQLAlchemy / AMQP | Scheduler, API server, workers |
| 2 | **Connection** de Airflow `aws_default` | Variable de entorno `AIRFLOW_CONN_AWS_DEFAULT` (URI) | `aws://?region_name=us-east-2` | Logs remotos de tareas en `s3://…/airflow-logs/` |
| 3 | Conexiones de las tareas a **Neon** | `NEON_READ_URL`, `NEON_WRITE_URL` en `.env` | URI de PostgreSQL | DAGs bronze (lectura) y `gold_neon_writeback` (escritura) |
| 4 | Conexiones de las tareas a **S3** y a las **APIs HTTP** | Rol IAM de la EC2 + `S3_BUCKET`, `F5_API_URL`, `NAGER_BASE_URL` | Nombre del bucket / URL base | Todas las tareas bronze, silver y gold |

## 1. Las conexiones propias de Airflow (infraestructura)

Airflow necesita una base de datos para guardar las corridas de los DAGs y un broker para mandar las tareas a los workers de Celery. Se configuran con variables de entorno `AIRFLOW__<SECCION>__<CLAVE>`, que Airflow lee en lugar de `airflow.cfg`:

```yaml title="docker-compose.workers.yaml (los workers llegan al núcleo por su IP privada)"
AIRFLOW__CORE__EXECUTOR: CeleryExecutor
# metadata DB (Postgres on the core EC2)
AIRFLOW__DATABASE__SQL_ALCHEMY_CONN: postgresql+psycopg2://airflow:${POSTGRES_PASSWORD}@${NUCLEO_HOST}:5432/airflow
# Celery broker (RabbitMQ on the core EC2): where the scheduler puts the tasks
AIRFLOW__CELERY__BROKER_URL: amqp://${RABBITMQ_USER}:${RABBITMQ_PASSWORD}@${NUCLEO_HOST}:5672//
# where the workers write the result of each task
AIRFLOW__CELERY__RESULT_BACKEND: db+postgresql://airflow:${POSTGRES_PASSWORD}@${NUCLEO_HOST}:5432/airflow
# Airflow 3: workers report task state to the API server
AIRFLOW__CORE__EXECUTION_API_SERVER_URL: 'http://${NUCLEO_HOST}:8080/execution/'
```

**Cómo funciona:** el scheduler (núcleo) pone un mensaje en la cola de RabbitMQ `bronze`, `silver` o `gold`; el worker que escucha esa cola lo toma, corre la tarea y reporta el estado por la execution API. Los puertos 5432, 5672 y 8080 del núcleo están abiertos **solo para el security group de los workers**.

## 2. La Connection de Airflow `aws_default`

Una *Airflow Connection* es un conjunto de credenciales con nombre que los hooks de Airflow buscan por su `conn_id`. En vez de crearla a mano en *Admin → Connections* (se perdería si se recrea la base de metadatos), se declara como variable de entorno `AIRFLOW_CONN_<CONN_ID>` con una URI:

```yaml title="docker-compose.nucleo.yaml / docker-compose.workers.yaml"
AIRFLOW_CONN_AWS_DEFAULT: 'aws://?region_name=${AWS_DEFAULT_REGION:-us-east-2}'
AIRFLOW__LOGGING__REMOTE_LOGGING: 'true'
AIRFLOW__LOGGING__REMOTE_BASE_LOG_FOLDER: s3://${S3_BUCKET}/airflow-logs
AIRFLOW__LOGGING__REMOTE_LOG_CONN_ID: aws_default
```

La URI **no tiene llave de acceso**: cuando el provider de Amazon no encuentra llave, boto3 usa el **rol IAM de la EC2** (`hospedaplus-pipeline-role`) y obtiene credenciales temporales. Se usa para los logs: una tarea corre en la EC2 de workers, su log se sube a S3 y la UI del núcleo lo lee desde ahí.

```bash title="Revisarla desde cualquier contenedor de Airflow"
docker compose -f docker-compose.nucleo.yaml exec airflow-scheduler airflow connections get aws_default
docker compose -f docker-compose.nucleo.yaml exec airflow-scheduler \
  python -c "import boto3; print(boto3.client('sts').get_caller_identity()['Arn'])"   # shows the IAM role in use
```

## 3. Neon: variable de entorno + psycopg2

Los DAGs no usan un hook de Airflow para Neon. El string de conexión vive en el `.env` de los workers y el módulo compartido `dags/hospedaplus/lake.py` lo lee; si está vacío, la tarea falla a propósito con un mensaje claro.

```python title="dags/hospedaplus/lake.py"
def neon_url() -> str:
    url = os.getenv("NEON_READ_URL", "")
    if not url:
        raise RuntimeError("NEON_READ_URL is empty: set it in .env (role etl_reader)")
    return url
```

```python title="dags/hospedaplus/neon.py: cada lectura devuelve JSON Lines"
def dump(sql: str, params: tuple = ()) -> tuple[bytes, int]:
    with psycopg2.connect(neon_url()) as conn, conn.cursor() as cur:
        cur.execute(sql, params)
        cols = [c.name for c in cur.description]
        rows = cur.fetchall()
    lines = [json.dumps(dict(zip(cols, r)), default=str, ensure_ascii=False) for r in rows]
    return ("\n".join(lines) + ("\n" if lines else "")).encode(), len(rows)
```

Solo una tarea escribe en Neon, con otro rol y otra variable:

```python title="dags/gold_neon_writeback.py"
url = os.getenv("NEON_WRITE_URL", "")          # role app_writer
with psycopg2.connect(url) as conn, conn.cursor() as cur:   # one transaction: all rows or none
    cur.executemany(UPSERT, rows)
```

```bash title=".env de la EC2 de workers (placeholders: nunca subas los valores reales)"
NEON_READ_URL=postgresql://etl_reader:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech/hospedaplus?sslmode=require
NEON_WRITE_URL=postgresql://app_writer:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech/hospedaplus?sslmode=require
```

## 4. S3 y las APIs HTTP

**S3 con boto3.** No hay llave ni en el código ni en `.env`: `boto3.client("s3")` encuentra solo el rol IAM de la EC2. `S3_ENDPOINT_URL` está vacío en AWS y solo se llena para pruebas locales con MinIO.

```python title="dags/hospedaplus/lake.py"
BUCKET = os.getenv("S3_BUCKET", "hospedaplus-lakehouse")

def s3_client():
    return boto3.client("s3", endpoint_url=os.getenv("S3_ENDPOINT_URL") or None)

def put(key: str, body: bytes, content_type: str = "application/json") -> str:
    s3_client().put_object(Bucket=BUCKET, Key=key, Body=body, ContentType=content_type)
    return f"s3://{BUCKET}/{key}"
```

**S3 con Spark.** Spark usa el protocolo `s3a://` (jars `hadoop-aws` + `aws-java-sdk-bundle` en la imagen) y el mismo rol IAM a través de `DefaultAWSCredentialsProviderChain`:

```python title="spark_jobs/session.py"
SparkSession.builder.appName(app).master("local[*]")
    .config("spark.jars", jars)
    .config("spark.hadoop.fs.s3a.impl", "org.apache.hadoop.fs.s3a.S3AFileSystem")
    .config("spark.hadoop.fs.s3a.aws.credentials.provider",
            "com.amazonaws.auth.DefaultAWSCredentialsProviderChain")

def path(layer: str, name: str) -> str:
    return f"s3a://{os.getenv('S3_BUCKET')}/{layer}/{name}"     # s3a://bucket/silver/reservas
```

**APIs HTTP con requests.** La URL base viene del `.env` y la API key opcional va en un header:

```python title="dags/bronze_f5_reviews.py"
base = os.getenv("F5_API_URL", "").rstrip("/")
headers = {"x-api-key": os.environ["F5_API_KEY"]} if os.getenv("F5_API_KEY") else {}
r = requests.get(f"{base}/api/v1/reviews", headers=headers, timeout=60,
                 params={"updated_from": data_interval_start.isoformat(), "page": page, "page_size": 100})
```

## Por qué variables de entorno en vez de hooks para Neon y S3

| Razón | Detalle |
| --- | --- |
| Un solo lugar para todo | El mismo `.env` configura Airflow, los DAGs y los jobs de Spark; los jobs de Spark corren fuera de los hooks de Airflow de todos modos. |
| Sobrevive a una reconstrucción | No se guarda nada en la base de metadatos, así que recrear Postgres no pierde ninguna conexión. |
| Mismo código en el CI | Las pruebas corren el código de los DAGs con variables falsas, sin necesitar la UI de Airflow. |
| Cero llaves de AWS | El acceso a S3 viene del rol IAM; no hay nada que rotar ni que se pueda filtrar. |

## Lo mismo con hooks de Airflow (opcional)

Los providers de Amazon y Postgres ya están instalados (`apache-airflow-providers-amazon==9.16.0`, `apache-airflow-providers-postgres==6.4.0`), así que el proyecto puede pasarse a hooks sin cambiar la imagen. Declara la conexión como URI:

```bash title=".env (ejemplo, placeholders)"
AIRFLOW_CONN_NEON_READER='postgresql://etl_reader:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech:5432/hospedaplus?sslmode=require'
```

```python title="Una tarea que usa los hooks"
from airflow.providers.postgres.hooks.postgres import PostgresHook
from airflow.providers.amazon.aws.hooks.s3 import S3Hook

@task(queue="bronze")
def copy_hotels():
    rows = PostgresHook(postgres_conn_id="neon_reader").get_records("SELECT * FROM operation.hotels")
    body = "\n".join(json.dumps(r, default=str) for r in rows)
    S3Hook(aws_conn_id="aws_default").load_string(body, key="bronze/neon_dims/hotels/test.jsonl",
                                                  bucket_name="hospedaplus-lakehouse-buenavista", replace=True)
```

Ambos enfoques abren las mismas conexiones; el proyecto usa variables de entorno por las razones de arriba.

## Conectar DAGs entre sí: Assets

Los DAGs también están "conectados" entre ellos, sin horas fijas, mediante **Assets** (Airflow 3). Una tarea declara lo que escribe con `outlets=` y un DAG declara lo que espera con `schedule=`:

```python title="dags/hospedaplus/lake.py + dags/silver_reservas_daily.py"
BRONZE_F3_RESERVATIONS = Asset("s3://hospedaplus-lakehouse/bronze/f3_reservations")

@task(queue="bronze", outlets=[BRONZE_F3_RESERVATIONS])      # bronze: "I updated this"
def f3_reservations(...): ...

@dag(schedule=((SILVER_FX_DAILY & BRONZE_F3_FULL & BRONZE_NEON_DIMS) | BRONZE_F3_RESERVATIONS))
def silver_reservas_daily(): ...                              # silver: runs when its inputs change
```

`&` espera a todos los assets, `|` corre cuando cualquiera cambia. Ver [DAGs](./dags.mdx) y [Cómo conectarse a Neon y S3](./how-to-connect.mdx).
