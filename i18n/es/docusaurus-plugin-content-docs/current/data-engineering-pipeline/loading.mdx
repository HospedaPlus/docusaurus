# Carga incremental y por lotes (batch)

El pipeline usa **las dos**: carga incremental donde los datos cambian todo el tiempo y deben llegar rápido, y carga por lotes (batch) donde importa más una imagen completa y consistente que la velocidad. Esta página muestra cuál usa cada paso, el código que lo hace y por qué.

| Paso | Tipo | Ventana | Por qué |
| --- | --- | --- | --- |
| `bronze_neon_f2_f3` | Incremental | cada hora, filas cambiadas en `[inicio, fin)` | Las reservas cambian todo el día; silver queda ~1 h detrás de Neon |
| `bronze_f5_reviews` | Incremental | cada hora, `updated_from` = inicio de la hora | Reseñas nuevas y editadas cada 15 min; solo se descarga la diferencia |
| `bronze_f7_fx` | Incremental (diaria) | un archivo por día | Una publicación de tasas por día |
| `bronze_neon_full_load` | Batch (foto completa) | cada noche, tablas enteras | Historial del seed + cuadra el lago con Neon; inventario consistente |
| `bronze_neon_dims`, `bronze_f6_events` | Batch (copia completa) | cada noche | Catálogos pequeños: copiar todo es más barato que seguir cambios |
| `bronze_f6_holidays` | Batch | mensual, año actual + siguiente | Los festivos casi no cambian |
| `bronze_f4_agencias` | Batch | semanal (lunes) | Las agencias envían un archivo por semana |
| `bronze_f1_historical` | Batch (una vez) | una vez | Historial fijo 2015–2017 |
| Silver y gold | Batch (reconstrucción completa) | después de sus entradas, sobrescribe | ~2 min con este volumen; siempre correcto y repetible |
| `gold_neon_writeback` | Upsert incremental | después de gold | Actualiza solo las filas (hotel, rango) en Neon |

## 1. Incremental por ventana de tiempo (Neon → bronze, cada hora)

Airflow le da a cada corrida horaria su propio intervalo de datos `[data_interval_start, data_interval_end)`. La consulta toma exactamente esas filas y el archivo se nombra por el intervalo. **Qué hace:** copia solo lo que cambió en esa hora. **Por qué:** consultas pequeñas y rápidas sobre Neon; ninguna fila se copia dos veces; una hora fallida se repite sola (Clear) y sobrescribe el mismo archivo. `updated_at` lo pone un trigger en cada cambio, así una cancelación días después se recoge en su propia hora.

```python title="dags/bronze_neon_f2_f3.py"
F2_SQL = """
SELECT * FROM streaming.reservation_event_ledger
 WHERE received_at >= %s AND received_at < %s
"""
F3_SQL = """
SELECT * FROM operation.reservations WHERE updated_at >= %s AND updated_at < %s
"""

def _key(prefix, start):          # one file per hour: re-running the hour overwrites it
    return f"bronze/{prefix}/fecha={start:%Y-%m-%d}/hora={start:%H}.jsonl"

@dag(schedule="@hourly", catchup=False, default_args={"retries": 3, "retry_exponential_backoff": True})
def bronze_neon_f2_f3():
    @task(queue="bronze", outlets=[BRONZE_F3_RESERVATIONS])
    def f3_reservations(data_interval_start=None, data_interval_end=None):
        body, n = dump(F3_SQL, (data_interval_start, data_interval_end))
        put(_key("f3_reservations", data_interval_start), body, "application/x-ndjson")
```

## 2. Incremental a través de una API (reseñas F5)

**Qué hace:** pide a la API solo las reseñas creadas o editadas desde el inicio de la hora, página por página. **Por qué:** descargar todo el historial de reseñas cada hora crecería sin fin; el filtro `updated_from` mantiene cada llamada pequeña, y las reseñas editadas vuelven para que silver se quede con la versión más reciente.

```python title="dags/bronze_f5_reviews.py"
items, page = [], 1
while True:
    r = requests.get(f"{base}/api/v1/reviews", params={
        "updated_from": data_interval_start.isoformat(), "page": page, "page_size": 100})
    body = r.json()
    items += body["items"]
    if page >= body.get("total_pages", 1):
        break
    page += 1
# the API only filters "from": keep [start, end) so two hours never overlap
items = [i for i in items if pendulum.parse(i["updated_at"]) < data_interval_end]
```

## 3. Batch: foto completa nocturna (Neon → bronze)

**Qué hace:** copia tablas enteras en una sola transacción de solo lectura `REPEATABLE READ`, en páginas de 50.000 filas por `id`, y escribe `_SUCCESS` solo al final. **Por qué:** la copia horaria no puede traer el historial creado antes del pipeline, y el inventario debe cuadrar con las reservas en un mismo instante. La paginación por clave (`id > último`) mantiene la memoria plana y `_SUCCESS` le dice a silver que la foto está completa.

```python title="dags/bronze_neon_full_load.py"
with psycopg2.connect(neon_url()) as conn:
    conn.set_session(isolation_level="REPEATABLE READ", readonly=True)   # one instant for all tables
    with conn.cursor() as cur:
        for table, prefix in TABLES.items():
            counts[table], parts[prefix] = _copy(cur, table, prefix, day)

def _copy(cur, table, prefix, day):            # keyset pagination, 50,000 rows per part
    last, part = 0, 0
    while True:
        cur.execute(f"SELECT * FROM operation.{table} WHERE id > %s ORDER BY id LIMIT %s", (last, PAGE))
        body, n = _jsonl(cur)
        if n == 0:
            break
        put(f"bronze/{prefix}/fecha={day}/part-{part:05d}.jsonl", body)
        last = json.loads(body.rstrip(b"\n").rsplit(b"\n", 1)[-1])["id"]
        part += 1
    ...
for prefix, n in parts.items():                # only when everything was copied
    _clean(prefix, day, n)                     # delete parts left by an older run of the same day
    put(f"bronze/{prefix}/fecha={day}/_SUCCESS", json.dumps(counts).encode())
```

## 4. Las dos combinadas en silver (reconstrucción batch sobre foto + incrementos)

**Qué hace:** lee la foto completa más reciente más los archivos horarios desde el día anterior a ella, se queda con la versión más nueva de cada reserva y **sobrescribe** la tabla silver. **Por qué:** la foto garantiza que esté todo, los incrementos agregan lo que cambió desde entonces, y sobrescribir completo hace a silver idempotente: repetir da la misma tabla, sin lógica de merge que pueda desviarse.

```python title="spark_jobs/silver_reservas.py"
# silver_reservas: newest snapshot + hourly increments, deduplicated, then full overwrite
full_d, hour_d = plan_days(partitions("bronze", "f3_reservations_full", complete=True),
                           partitions("bronze", "f3_reservations"))
raw = _union(_with_src(_read_days(s, "f3_reservations_full", full_d, RES_COLS), 0),
             _with_src(_read_days(s, "f3_reservations", hour_d, RES_COLS), 1))
reservas = transform(raw, hotels, channels, room_types, fx)
check(reservas, cancel)
reservas.write.mode("overwrite").partitionBy("source").parquet(path("silver", "reservas"))
```

## 5. Upsert incremental de vuelta a Neon

**Qué hace:** inserta o actualiza una fila por hotel y rango de anticipación en una sola transacción. **Por qué:** Neon es la base operacional en vivo; un upsert cambia solo esas filas y nunca deja la tabla a medio escribir.

```python title="dags/gold_neon_writeback.py"
UPSERT = """
INSERT INTO operation.cancellation_rate_by_lead (hotel_code, lead_bucket, cancel_rate, updated_at)
VALUES (%s, %s, %s, NOW())
ON CONFLICT (hotel_code, lead_bucket) DO UPDATE
   SET cancel_rate = EXCLUDED.cancel_rate, updated_at = EXCLUDED.updated_at
"""
with psycopg2.connect(url) as conn, conn.cursor() as cur:   # one transaction: all rows or none
    cur.executemany(UPSERT, rows)
```

**En resumen:** bronze es incremental donde el dato está vivo (reservas, eventos, reseñas) y batch donde importa estar completo (foto, catálogos, archivos); silver y gold son reconstrucciones batch que leen ambos.
