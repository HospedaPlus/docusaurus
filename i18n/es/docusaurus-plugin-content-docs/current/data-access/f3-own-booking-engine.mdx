# <SourceTitleIcon icon="database" tone="teal" />F3 · Motor de reservas propio <SourceType>Base de datos PostgreSQL</SourceType>

Base operativa simulada del motor de reservas propio de la cadena. Tiene el catálogo de hoteles, el inventario de habitaciones, las tarifas por temporada y las reservas directas y corporativas. También es donde terminan las reservas de los demás canales (OTA de F2, agencias de F4), a través de una sola función de reserva.

## Cómo se simula

Dos trabajos, ambos con la imagen del repositorio:

1. **Semilla** (`python -m seed all`). Carga el catálogo, 365 noches de inventario y tarifas hacia adelante, 60.000+ huéspedes y la historia de reservas (`dev`: 90 noches pasadas, `full`: 400). Los hoteles urbanos reciben más llegadas de domingo a martes, los resorts en fin de semana, la temporada alta trae más huéspedes y la ocupación futura baja mientras más lejos se mira, como en una curva de reservas real. Misma semilla + misma fecha de inicio = los mismos datos, fila por fila.
2. **Simulador** (`python -m seed simulate`). Corre todo el tiempo en AWS EC2. Cada 10 segundos reserva una estadía directa o corporativa con `operation.reservar()` (`rejected` cuando el hotel está lleno), de vez en cuando cancela una con `operation.cancelar()`, sigue inyectando filas malas y una vez al día pone a la venta una noche nueva a 365 días.

### Frecuencia y volumen

- `SIM_BOOKINGS_PER_MIN=6`: unos 8.600 intentos de reserva al día, así que F3 es una fuente continua y el pipeline siempre encuentra filas nuevas.
- `SEED_MODE=full` carga la historia completa; `dev` es una versión pequeña para desarrollo.
- `python -m seed check` corre 24 controles de salud e integridad y solo pasa si pasan todos (conteos, catálogo, sin huérfanos, inventario = reservas confirmadas, ninguna reserva antes del día en que se hizo).

## Dónde se almacena

```text
semilla + simulador ─► Neon operation ◄─ consumidor F2 y cargador F4 (el mismo reservar())
Neon ─► Airflow bronze_neon_f2_f3 (cada hora, por updated_at) ─► S3 bronze/f3_reservations/, f3_anomalies/
Neon ─► Airflow bronze_neon_full_load (foto nocturna)          ─► S3 bronze/f3_*_full/
Neon ─► Airflow bronze_neon_dims (catálogo nocturno)           ─► S3 bronze/neon_dims/
```

Neon es el almacén operativo. El lago recibe F3 de dos formas: cada hora, las filas que cambiaron desde la corrida anterior (`reservations.updated_at` lo pone un trigger en cada cambio), y cada noche una foto completa de reservas, anomalías, inventario, reubicaciones y rechazos, tomada en una sola transacción y marcada con `_SUCCESS`. La tabla `guests` nunca se copia: los datos personales se quedan en Neon.

## Cómo acceder

| Propiedad | Valor |
| --- | --- |
| Host | Endpoint de Neon de la rama `production` (host con `-pooler` para los clientes, host directo para la semilla) |
| Puerto | `5432` |
| Base de datos | `hospedaplus` |
| SSL | `sslmode=require` |

Cada cliente usa su propio rol. Pide al equipo las cadenas de conexión: nunca se escriben en el repositorio ni en este sitio.

| Rol | Lo usa | Puede |
| --- | --- | --- |
| `hospedaplus_owner` | Semilla y migraciones | Todo. |
| `app_writer` | Consumidor F2, simulador F3, cargador F4, escritura de vuelta del pipeline | Leer y escribir datos; no cambia el esquema. |
| `etl_reader` | Worker bronze de Airflow, equipo (DBeaver, psql) | Solo lectura. |

## Qué contiene

| Tabla | Contenido |
| --- | --- |
| `hotels`, `room_types`, `rooms` | 28 hoteles (`HP-CO-001`…) con zona horaria y moneda; `SINGLE`, `DOUBLE`, `TWIN`, `SUITE`; 4.000 habitaciones. |
| `channels` | 21 canales de venta con su comisión (RN-02). |
| `rates` | Precio por noche por hotel, tipo de habitación y temporada (RN-05). |
| `inventory` | Habitaciones totales, vendidas y límite de sobreventa por hotel, tipo de habitación y noche (RN-03). |
| `guests` | Huéspedes `G-0000001`…, con el mismo `guest_ref` y nivel de fidelidad que F2 (datos personales, RN-11). |
| `reservations` | Reservas de todos los canales, con cancelaciones, no-shows y penalidades. |
| `reservation_anomalies` | Filas con problemas de calidad conocidos, separadas a propósito. |
| `reservation_rejections`, `relocations` | Reservas rechazadas por falta de cupo (RN-04), reservas reubicadas. |
| `cancellation_policies`, `cancellation_rate_by_lead` | Políticas por canal (RN-07); tasas de cancelación que escribe de vuelta el pipeline. |
| `local_events` | Los eventos locales de F6. |

<AccessNote icon="alert" title="Problemas de calidad de datos conocidos">

Las filas que romperían las restricciones van a `reservation_anomalies` (2% cada una por defecto, `SEED_ZERO_GUESTS_RATE` y `SEED_INVALID_DATES_RATE`), tanto en la semilla como en el simulador continuo:

- Reservas con cero huéspedes.
- Fechas de salida anteriores a la fecha de llegada.

</AccessNote>
