# Arquitetura v2

Esta é a arquitetura de dados atual da HospedaPlus Revenue na AWS (região us-east-2, Ohio). Os dados avançam da esquerda para a direita por cinco blocos: as fontes, a entrada na AWS, o processamento dentro da VPC de produção, o lakehouse com seu catálogo e o analytics usado para decidir os preços. Uma camada de segurança e observabilidade atravessa todos eles.

## Bloco por bloco

### 1. Fontes de dados

- **Hóspedes (web / app)** fazem reservas diretas e corporativas no motor de reservas próprio da rede (F3). As requisições passam pelo Route 53.
- **F2 · Channel Manager** envia ao RabbitMQ os eventos das OTAs (reservas, cancelamentos e tarifas).
- **As APIs públicas F5, F6 e F7** (avaliações e demais fontes externas) são extraídas uma vez por dia via HTTPS, saindo pelo NAT Gateway.
- **F1 Kaggle e F4 agências** chegam como arquivos: o histórico do Kaggle uma única vez e os CSVs das agências todos os dias, em `s3://…/landing` e de lá para o Bronze.
- **GitHub Actions (CI/CD)** é o pipeline da equipe de desenvolvimento: roda o pytest, gera as imagens, envia-as para o Amazon ECR e faz o deploy no ECS Fargate (detalhes abaixo).

### 2. Entrada

- **Route 53** resolve o DNS da API de reservas.
- **AWS WAF** limita a quantidade de requisições e aplica as regras OWASP antes de o tráfego chegar ao Internet Gateway.
- **Amazon ECR** guarda as imagens do FastAPI, dos consumidores e do Airflow, que são implantadas a partir dali.

### 3. Processamento — VPC de produção

- **Sub-rede pública:** o Internet Gateway deixa o tráfego entrar, o Application Load Balancer termina o HTTPS e o encaminha ao FastAPI, e o NAT Gateway dá às sub-redes privadas uma saída para as APIs externas e o Neon.
- **Sub-rede privada, tempo real:** o FastAPI no ECS Fargate responde à disponibilidade e às reservas diretas e recebe os webhooks da F2; uma reserva direta é gravada no Neon com um `UPDATE` condicional. O Amazon MQ (RabbitMQ) transporta os eventos e tarifas da F2 em `/streaming` e atua como broker do Celery em `/airflow`. Os consumidores no Fargate leem `q.operacion` para aplicar os eventos no Neon e `q.bronze` para gravá-los no Bronze a cada 5 minutos.
- **Sub-rede privada, batch:** um EC2 `t3.medium` roda o Airflow 3 com o CeleryExecutor (API Server, Scheduler, DAG Processor e BD de metadados). Outro EC2 `t3.xlarge` roda três workers do Celery com Spark: *bronze* (Python, extrai do Neon, das APIs e dos arquivos), *silver* (Spark: valida, deduplica, pseudonimiza e converte os valores para COP) e *gold* (Spark: tabelas `dim_` / `fact_` e tarifas horárias). Se o Spark ficar sem memória, só cai o EC2 dos workers, não o Scheduler.
- **Neon PostgreSQL 16 (SaaS externo)** é o banco operacional da F3: 28 hotéis e 4.000 quartos, com branches `production` e `dev`. O worker bronze lê reservas, canais e tarifas de forma incremental com um papel somente leitura.
- **O endpoint do S3 do tipo gateway** (gratuito) permite que os workers gravem Parquet no S3 sem passar pelo NAT.

### 4. Lakehouse e catálogo

- A HospedaPlus usa um **lakehouse**: os dados ficam como arquivos Parquet no Amazon S3, e o Glue Data Catalog e o Athena permitem que o negócio os consulte com SQL diretamente sobre o S3, sem um warehouse separado.
- O bucket **`hospedaplus-datalake`** é criptografado com SSE-KMS e guarda Parquet particionado por data, com uma única cópia por camada:
  - **Bronze:** os dados como chegam (eventos da F2 a cada 5 minutos e as extrações diárias); vão para o Glacier após 90 dias.
  - **Silver:** gravado pelo Spark; limpo, tipado e sem duplicados, com as anomalias em quarentena e sem dados pessoais.
  - **Gold:** gravado pelo Spark como modelo estrela (`dim_` / `fact_`); é a única camada que o negócio consulta e vive só aqui.
- Quando o Gold termina, o Airflow inicia o **Glue Crawler**, que lê `silver/` e `gold/` e registra tabelas e partições no **Glue Data Catalog**.
- O **Amazon Athena** usa esse catálogo para consultar os Parquet com SQL, sem copiá-los para outro banco, e cobra por dado escaneado. Os resultados vão para `s3://…/athena-results/` e são apagados após 7 dias.

### 5. Analytics e decisão

- **Power BI** (preferido) se conecta ao Athena pelo conector ODBC, com atualização agendada através de um gateway.
- **Metabase** (alternativa) é open source e tem conector nativo para o Athena; ainda está em avaliação.
- **O Revenue Manager e os gerentes de hotel** usam esses dashboards para decidir preço e ocupação por hotel.

### CI/CD com GitHub Actions

O GitHub Actions é o pipeline de CI/CD da equipe e é o que conecta o código ao Amazon ECR e ao Amazon ECS:

1. Roda os testes com pytest.
2. Gera as imagens Docker do FastAPI, dos consumidores e do Airflow.
3. Envia essas imagens para o Amazon ECR.
4. Faz o deploy das novas imagens nos serviços do ECS Fargate (FastAPI e consumidores). Os EC2 do Airflow também usam imagens do ECR.

### Segurança e observabilidade

| Serviço | Função |
| --- | --- |
| IAM | Papéis dos EC2 (S3, Glue, segredos) e das tarefas Fargate; pessoas com MFA e privilégio mínimo. |
| KMS | Uma chave própria criptografa o bucket S3, os discos EBS, os segredos e o Amazon MQ. |
| Secrets Manager | URLs do Neon por papel, usuários do RabbitMQ e API keys. Nada disso vai no repositório. |
| CloudWatch | Logs do FastAPI, dos consumidores e do Airflow; alarmes para 5xx do ALB, fila crescendo, DAG com falha e custo. |
| CloudTrail | Auditoria de quem leu um segredo, mudou permissões IAM ou apagou dados no S3. |
| Systems Manager | Acesso aos EC2 e à UI do Airflow sem SSH nem portas abertas (Session Manager). |

## Fluxos de dados

As cores do diagrama seguem a legenda:

- **Tempo real (rosa):** hóspede → Route 53 → WAF → ALB → FastAPI → Neon, e F2 → RabbitMQ → consumidores → Neon.
- **CI/CD e controle do Airflow (roxo, tracejado):** GitHub Actions → ECR → FastAPI e o EC2 do Airflow; o RabbitMQ também é o broker do Celery entre o núcleo do Airflow e os workers.
- **Batch (azul):** fontes → worker bronze → Bronze → Silver → Gold, gravado pelo endpoint do S3.
- **Metadados (verde-azulado, tracejado):** Glue Crawler → Glue Data Catalog → Athena.
- **Tarifas horárias (laranja):** worker gold → RabbitMQ → consumidor → Neon.
- **Consumo do Gold (verde):** Gold → Athena → Power BI ou Metabase → gerentes.
