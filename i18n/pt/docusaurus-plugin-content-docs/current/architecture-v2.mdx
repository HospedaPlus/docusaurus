# Architecture v2

Esta é a arquitetura final do HospedaPlus Revenue na AWS (região **us-east-2, Ohio**): três EC2 com Docker Compose, Kafka para a F2, Airflow 3.1.5 com Celery sobre RabbitMQ, Spark em modo local nos workers, S3 + Athena (Glue Data Catalog preenchido com DDL) e Power BI por ODBC.

## Mudanças em relação à versão anterior

| Antes | Agora | Por quê |
| --- | --- | --- |
| Spark no Fargate / EMR | **Spark local** na EC2 de workers (t3.xlarge) | ~200.000 reservas cabem em uma máquina; nenhum cluster para pagar ou operar |
| Amazon ECR | **GitHub Container Registry (GHCR)** | As imagens são construídas pelo CI junto ao código |
| Glue Crawler | **Athena DDL** (`CREATE EXTERNAL TABLE`) | A conta não permite crawlers; o DDL dá nomes e tipos exatos |
| EKS, ALB, WAF, NAT, Secrets Manager | Não usados | Não são necessários neste tamanho; os segredos ficam em `.env` fora do repo e nos segredos do GitHub |
| Limites de overbooking calculados na operação | **Write-back do gold para o Neon** | A operação usa as mesmas taxas de cancelamento que o negócio vê |
| Preços da F2 pelo RabbitMQ | **F2 pelo Kafka** até o Neon | O RabbitMQ é só o broker do Celery |
| Kafka e simuladores espalhados | Uma **EC2 de fontes** | Uma máquina para todos os simuladores |

## Bloco a bloco

### 1. Fontes e equipe

- **Equipe dev · GitHub Actions**: ruff, pytest e validação de DAGs; a cada merge envia uma imagem ao GHCR e faz deploy por SSH.
- **Equipe de dados**: entra nas máquinas por SSH e abre as UIs do Airflow (`:8080`) e do Flower (`:5555`).
- **Produtor F2** (eventos OTA, contrato 1.3) e **simulador F3** (`seed simulate`, reservas diretas, papel `app_writer`).
- **APIs F5 · F6 · F7**: a API de avaliações da equipe (FastAPI no ECS), Nager.Date e Frankfurter, lidas por HTTPS.
- **F1 Kaggle**: `hotel_bookings.csv` do repo `hospedaplus-csv`, carregado uma vez.
- **Catálogo compartilhado**: a fonte canônica é o `db_simulated` (Neon); F2, F4 e F5 usam seus códigos de hotel, tipo de quarto, canal e moeda.

### 2. Entrada

- **GHCR** guarda as imagens (`ghcr.io/hospedaplus/…`, tags `:sha`, `:main` e `vX.Y.Z`).
- **Internet Gateway** para a VPC (sub-rede pública, IPs públicos).
- **Security groups**: `sg-nucleo` abre 22, 8080, 5555 e 15672 só para o IP da equipe, 80/443 para o Nginx (as [UIs de monitoramento](./data-engineering-pipeline/monitoring.mdx)), e 5432, 5672 e 8080 só para `sg-workers`; `sg-workers` abre 22 para a equipe. Os workers chegam ao núcleo pelo **IP privado**.

### 3. Processamento: EC2 em us-east-2

- **EC2 de fontes** (Docker Compose): `buenavista-streaming` (produtor F2 → **Kafka 4.1.1**, tópico `reservation.events.v1_3`, 6 partições + DLQ → 6 `neon-consumer` que chamam `reservar()`), `db_simulated` (F3 `seed simulate`) e `hospedaplus-csv` (`f4-weekly`, segunda 06:00 UTC, 15 agências → S3 e Neon).
- **EC2 núcleo** (t3.medium, 30 GB): Airflow 3.1.5 com CeleryExecutor (API server, scheduler, DAG processor, triggerer, PostgreSQL de metadados), RabbitMQ (filas `bronze`, `silver`, `gold`) e Flower.
- **EC2 workers** (t3.xlarge, 50 GB): três workers Celery. **bronze** roda 4 tarefas por vez (Python: Neon, APIs F5–F7, F1 e F4 → `bronze/`); **silver** roda 2 (Spark local: valida, deduplica, converte para COP); **gold** roda 2 (Spark local: `dim_`, `fact_`, `mart_` P1–P5 e o write-back). O Spark 3.5 lê e grava no S3 com `s3a://` usando o papel IAM da EC2. Detalhes em [Computação e recursos](./data-engineering-pipeline/compute-resources.mdx).

### OLTP: Neon PostgreSQL (SaaS externo)

Esquemas `operation` e `streaming`, branches `development` e `production`, e `reservar()` com o limite de overbooking (hoje 0). O pipeline o lê com `etl_reader` a cada hora e com uma cópia completa às 03:00 UTC, e devolve as taxas de cancelamento com `app_writer`.

### 4. Data lake (OLAP)

- **Amazon S3 `hospedaplus-lakehouse-buenavista`**, acesso público bloqueado: `bronze/` (JSON/CSV como extraído), `silver/` (Parquet: reservas, cancelamentos, ocupação, calendário, avaliações, câmbio, histórico F1), `gold/` (Parquet: 4 dims, 4 facts, 7 marts, e um JSON para o write-back ao Neon), `airflow-logs/` e `athena-results/`.
- Cada DAG publica um **Asset** ao terminar e o próximo começa sozinho.
- **Athena DDL → Glue Data Catalog** (`hospedaplus_gold`, refeito só se um esquema mudar) → **Amazon Athena** (workgroup `primary`).

### 5. Análise e decisão

O **Power BI Desktop** lê o gold com o driver ODBC do Amazon Athena (x64) como o usuário IAM somente leitura `powerbi-reader`; o relatório tem 4 páginas. O **Revenue Manager e os gerentes** o usam para decidir preço e ocupação por hotel. Veja [Visualização de dados](./data-visualization/index.mdx).

## Segurança e operação: o que está configurado hoje

| Área | O que existe |
| --- | --- |
| IAM | Papel `hospedaplus-pipeline-role` no núcleo e nos workers, só sobre o bucket. Usuário `powerbi-reader`: Athena, Glue e S3, somente leitura. |
| Security groups | `sg-nucleo`, `sg-workers`: portas abertas só para o IP da equipe e entre os dois grupos. |
| Credenciais | `.env` em cada EC2 (fora do repo), segredos de deploy no GitHub, chaves da AWS vazias (o papel as fornece). |
| Papéis do Neon | `hospedaplus_owner` (migrações), `app_writer` (consumidores, simuladores, write-back), `etl_reader` (Airflow). |
| S3 | Acesso público bloqueado; logs do Airflow em `airflow-logs/`, resultados do Athena em `athena-results/`. |
| Monitoramento | Flower para os workers, a UI do Airflow, `docker compose logs` e o lag do grupo do Kafka. Veja [Monitoramento](./data-engineering-pipeline/monitoring.mdx). |

## Fluxos de dados (legenda)

- **Tempo real / OLTP (rosa):** eventos F2 pelo Kafka e cargas F3/F4 que chamam `reservar()` no Neon.
- **CI/CD e controle (roxo, tracejado):** imagens no GHCR, deploy por SSH, ordens do Airflow pelo RabbitMQ.
- **Batch / OLAP (azul):** extração para o bronze, depois bronze → silver → gold (workers Celery + Spark local).
- **Catálogo (verde-azulado, tracejado):** tabelas criadas com Athena DDL no Glue Data Catalog (sem crawler).
- **Write-back (laranja):** gold → Neon `operation.cancellation_rate_by_lead` (upsert diário).
- **Consumo do gold (verde):** Athena → Power BI (ODBC) → gerentes.
- **Pendente (cinza, tracejado):** API de negócio com FastAPI (US-41).
