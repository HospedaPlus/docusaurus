## Como acessar

O banco de dados compartilhado da equipe roda no Neon (PostgreSQL 16 gerenciado), carregado no modo `full` e verificado com `python -m seed check`.

| Propriedade | Valor |

| Papel | Usado por | Pode |

### Host pooled ou direto

O host `-pooler` coloca o PgBouncer na frente do banco, assim muitas conexões de clientes compartilham poucas conexões reais. Ele funciona em modo de transação, então tudo o que precisa de uma sessão fixa (um `SET` duradouro, tabelas temporárias, cargas em massa longas) vai para o host direto.

| Cliente | Host |
| --- | --- |
| FastAPI, consumidores Kafka, Airflow | Pooled |
| Seed (`init`, carga com `COPY`) | Direto (o mesmo host sem `-pooler`) |
| Equipe no DBeaver ou psql | Pooled |

- No DBeaver ou pgAdmin, crie uma conexão PostgreSQL com os dados acima e defina o modo SSL como `require`.
- O banco de dados hiberna após 5 minutos sem uso e acorda na próxima consulta, então a primeira consulta pode levar alguns segundos.
- Para rodar o seed localmente, o repositório inclui um arquivo Docker Compose com PostgreSQL 16 na porta `5437`, para nunca conflitar com o Neon.

## O que contém

| Tabela | Conteúdo |
| --- | --- |
| `hotels` | 28 hotéis urbanos e resorts, com código (`HP-CO-001`…), cidade, país, fuso horário e moeda. |
| `room_types` | `SINGLE`, `DOUBLE`, `TWIN` e `SUITE`, com o máximo de hóspedes. |
| `rooms` | Os 4.000 quartos físicos, por hotel e tipo de quarto. |
| `channels` | 21 canais de venda com sua comissão (RN-02). |
| `rates` | Preço por noite por hotel, tipo de quarto e temporada (`LOW`, `MID`, `HIGH`, RN-05). |
| `inventory` | Quartos totais e disponíveis por hotel, tipo de quarto e noite. |
| `guests` | Dados pessoais dos hóspedes, pseudonimizados antes da análise (RN-11). |
| `reservations` | Reservas diretas e corporativas, com cancelamentos e no-shows. |
| `reservation_anomalies` | Linhas com os problemas de qualidade de dados conhecidos, separadas de propósito. |

Hotéis, tipos de quarto e canais vêm do **catálogo compartilhado** que F2, F4 e F5 também leem, para que o pipeline possa cruzar todas as fontes.

## Seed de dados

Todos os dados são gerados pelo seed do repositório (`python -m seed`), nunca carregados à mão ou a partir de um dump. O seed:

- **É reproduzível.** O mesmo seed e a mesma data de início produzem os mesmos dados, linha por linha.
- **É idempotente.** Substitui os dados em uma única transação: executá-lo várias vezes deixa uma única cópia, e se falhar, os dados anteriores ficam intactos.
- **Tem dois volumes.** O modo `dev` cobre 90 noites passadas e 30 futuras; o modo `full` cobre 400 passadas e 180 futuras.
- **Simula uma demanda realista.** Hotéis urbanos recebem mais chegadas de domingo a terça, resorts no fim de semana, e a alta temporada traz mais hóspedes.
- **Nunca faz overbooking.** O gerador recusa uma reserva quando o tipo de quarto está lotado, e o banco rejeita `available_rooms < 0`.
- **Rejeita reservas no passado.** Um trigger rejeita qualquer reserva cujo check-in seja anterior ao dia em que foi feita.
- **É seguro por padrão.** Comandos destrutivos param em bancos remotos, a menos que se use `--allow-remote`.
- **Verifica a si mesmo.** `python -m seed check` executa 21 verificações de saúde e integridade e só passa se todas passarem.

| Comando | O que faz |
| --- | --- |
| `python -m seed init` | Cria as tabelas e os índices. |
| `python -m seed seed` | Esvazia as tabelas e carrega um novo conjunto de dados. |
| `python -m seed check` | Executa as verificações de saúde e integridade (somente leitura). |
| `python -m seed all` | `init` + `seed` + `check`. |

<AccessNote icon="alert" title="Problemas de qualidade de dados conhecidos">

As linhas que quebrariam as restrições vão para `reservation_anomalies` em vez de `reservations` (2% cada por padrão, configurável):

- Reservas com zero hóspedes.
- Datas de check-out anteriores à data de check-in.

</AccessNote>
