# <SourceTitleIcon icon="database" tone="teal" />F3 · Motor de reservas próprio <SourceType>Banco de dados PostgreSQL</SourceType>

Banco operacional simulado do motor de reservas próprio da rede. Tem o catálogo de hotéis, o inventário de quartos, as tarifas por temporada e as reservas diretas e corporativas. Também é onde terminam as reservas dos outros canais (OTA da F2, agências da F4), por meio de uma única função de reserva.

## Como é simulada

Dois jobs, ambos com a imagem do repositório:

1. **Seed** (`python -m seed all`). Carrega o catálogo, 365 noites de inventário e tarifas à frente, 60.000+ hóspedes e o histórico de reservas (`dev`: 90 noites passadas, `full`: 400). Hotéis urbanos recebem mais chegadas de domingo a terça, resorts nos fins de semana, a alta temporada traz mais hóspedes e a ocupação futura cai quanto mais longe se olha, como em uma curva de reservas real. Mesma semente + mesma data de início = os mesmos dados, linha por linha.
2. **Simulador** (`python -m seed simulate`). Roda o tempo todo na AWS EC2. A cada minuto reserva uma estadia direta ou corporativa com `operation.reservar()` (`rejected` quando o hotel está cheio), de vez em quando cancela uma com `operation.cancelar()`, continua injetando linhas ruins e uma vez por dia coloca à venda uma noite nova a 365 dias.

### Frequência e volume

- `SIM_BOOKINGS_PER_MIN=1` (assim está na EC2): cerca de 1.440 tentativas de reserva por dia, então a F3 é uma fonte contínua e o pipeline sempre encontra linhas novas.
- `SEED_MODE=full` carrega o histórico completo; `dev` é uma versão pequena para desenvolvimento.
- `python -m seed check` executa 24 verificações de saúde e integridade e só passa se todas passarem (contagens, catálogo, sem órfãos, inventário = reservas confirmadas, nenhuma reserva antes do dia em que foi feita).

## Onde é armazenada

<F3Flow />

O Neon é o armazenamento operacional. O lago recebe a F3 de duas formas: a cada hora, as linhas que mudaram desde a execução anterior (`reservations.updated_at` é preenchido por um trigger a cada mudança), e toda noite uma foto completa de reservas, anomalias, inventário, realocações e rejeições, tirada em uma única transação e marcada com `_SUCCESS`. A tabela `guests` nunca é copiada: os dados pessoais ficam no Neon.

## Como acessar

| Propriedade | Valor |
| --- | --- |
| Host | Endpoint do Neon da branch `production` (host com `-pooler` para os clientes, host direto para o seed) |
| Porta | `5432` |

Cada cliente usa seu próprio papel. Peça à equipe as strings de conexão: elas nunca são escritas no repositório nem neste site.

| Papel | Usado por | Pode |
| --- | --- | --- |
| `hospedaplus_owner` | Seed e migrações | Tudo. |
| `app_writer` | Consumidor F2, simulador F3, carregador F4, escrita de volta do pipeline | Ler e gravar dados; não altera o esquema. |
| `etl_reader` | Worker bronze do Airflow, equipe (DBeaver, psql) | Somente leitura. |

## Como colocar para rodar

Você precisa do Docker e do banco Neon com os esquemas e roles de [Conexão com o Neon](../data-engineering-pipeline/neon-connection.mdx). Rode o F3 **antes** do F2: o consumidor do F2 grava nas tabelas de `operation` que o seed do F3 cria.

```bash
# Baixa o repositório F3 e entra na pasta dele
git clone https://github.com/HospedaPlus/db_simulated.git && cd db_simulated
# Cria seu .env a partir do exemplo
cp .env.example .env
```

Preencha estas duas linhas do `.env` (copie de *Neon → Connect*; use só letras, números, `-` e `_` nas senhas, porque `@` ou `#` quebram a URL):

```bash
# Dono, host direto (sem -pooler): cria as tabelas e carrega o seed
NEON_OWNER_URL=postgresql://hospedaplus_owner:<password>@<endpoint>.us-east-2.aws.neon.tech/hospedaplus?sslmode=require
# app_writer, host com pool (-pooler): usado pelo simulador contínuo
NEON_APP_URL=postgresql://app_writer:<password>@<endpoint>-pooler.us-east-2.aws.neon.tech/hospedaplus?sslmode=require
```

```bash
# 1. Cria as tabelas e carrega catálogo, inventário, hóspedes e histórico (uma vez; substitui os dados)
docker compose --profile neon run --rm --build neon-seed
# 2. Carrega os 33 eventos locais (F6b) em operation.local_events
docker compose --profile neon run --rm --build neon-check events
# 3. Roda as 24 verificações de integridade: todas devem passar
docker compose --profile neon run --rm neon-check
# 4. Inicia o simulador em segundo plano (1 reserva por minuto com SIM_BOOKINGS_PER_MIN=1)
docker compose --profile neon up -d --build neon-simulator
```

**Verificação:** `SELECT count(*) FROM operation.hotels;` devolve 28, e depois de alguns minutos `SELECT max(created_at) FROM operation.reservations;` continua avançando.

Para testar sem o Neon, `docker compose up -d postgres && docker compose run --rm seed all` usa um PostgreSQL local. Como a imagem e os perfis são montados: [Docker](../devops/docker.mdx).

## O que contém

| Tabela | Conteúdo |
| --- | --- |
| `hotels`, `room_types`, `rooms` | 28 hotéis (`HP-CO-001`…) com fuso horário e moeda; `SINGLE`, `DOUBLE`, `TWIN`, `SUITE`; 4.000 quartos. |
| `channels` | 21 canais de venda com sua comissão (RN-02). |
| `rates` | Preço por noite por hotel, tipo de quarto e temporada (RN-05). |
| `inventory` | Quartos totais, vendidos e limite de overbooking por hotel, tipo de quarto e noite (RN-03). |
| `guests` | Hóspedes `G-0000001`…, com o mesmo `guest_ref` e nível de fidelidade da F2 (dados pessoais, RN-11). |
| `reservations` | Reservas de todos os canais, com cancelamentos, no-shows e multas. |
| `reservation_anomalies` | Linhas com problemas de qualidade conhecidos, separadas de propósito. |
| `reservation_rejections`, `relocations` | Reservas rejeitadas por falta de quartos (RN-04), reservas realocadas. |
| `cancellation_policies`, `cancellation_rate_by_lead` | Políticas por canal (RN-07); taxas de cancelamento gravadas de volta pelo pipeline. |
| `local_events` | Os eventos locais da F6. |

<AccessNote icon="alert" title="Problemas de qualidade de dados conhecidos">

As linhas que quebrariam as restrições vão para `reservation_anomalies` (2% cada por padrão, `SEED_ZERO_GUESTS_RATE` e `SEED_INVALID_DATES_RATE`), tanto no seed quanto no simulador contínuo:

- Reservas com zero hóspedes.
- Datas de saída anteriores à data de chegada.

</AccessNote>
