# Camada gold e modelo de dados

O gold é a camada analítica. Uma vez por noite `gold_modelo_daily` (`spark_jobs/gold_modelo.py`, fila `gold`) lê as tabelas silver e os últimos catálogos do Neon, reconstrói **todas** as tabelas gold por inteiro, verifica todas e as sobrescreve. Todos os valores estão em **COP** e reservas duplicadas (F4) nunca contam.

## Modelo de dados

### Qual modelo é: um esquema estrela

O modelo é um **esquema estrela**, não um floco de neve. Cada tabela de fatos se liga **diretamente** às suas dimensões, e nenhuma dimensão depende de outra: o país, a cidade e a categoria do hotel ficam dentro de `dim_hotel`, não em tabelas separadas `dim_pais` ou `dim_ciudad`. Algumas colunas descritivas (`channel_type`, `hotel_pais`) também são copiadas nos fatos para que os filtros mais comuns não precisem de nenhuma junção.

**Por que estrela e não floco de neve:** o motor do Power BI é feito para estrelas (relações um para muitos de cada dimensão para cada fato, filtros em um só sentido); as dimensões são pequenas (28 hotéis, poucos canais e tipos de quarto), então normalizá-las adicionaria junções sem economizar espaço; e o modelo fica fácil de ler para o negócio.

### Como ele é

```text
                              ┌──────────────────────┐
                              │      dim_fecha       │
                              │ PK fecha             │
                              │ anio, mes, semana…   │
                              └──────────┬───────────┘
                                         │
 ┌──────────────────────┐     ┌──────────┴───────────┐     ┌──────────────────────┐
 │      dim_canal       │     │        FATOS         │     │ dim_tipo_habitacion  │
 │ PK channel_code      ├─────┤ fact_reservas        ├─────┤ PK room_type         │
 │ channel_type, comis. │     │ fact_cancelaciones   │     │ nombre, capacidad    │
 └──────────────────────┘     │ fact_ocupacion_diaria│     └──────────────────────┘
                              │ fact_resenas         │
                              └──────────┬───────────┘
                                         │
                              ┌──────────┴───────────┐
                              │      dim_hotel       │
                              │ PK hotel_code        │
                              │ ciudad, pais, categ. │
                              └──────────────────────┘
                    os marts P1–P5 são construídos a partir dos fatos
```

Relações (todas um para muitos, da dimensão para o fato):

| Fato | `dim_fecha` | `dim_hotel` | `dim_canal` | `dim_tipo_habitacion` |
| --- | --- | --- | --- | --- |
| `fact_reservas` | `check_in`, `fecha_reserva`, `check_out` | `hotel_code` | `channel_code` | `room_type` |
| `fact_cancelaciones` | `check_in`, `fecha_cancelacion` | `hotel_code` | `channel_code` | `room_type` |
| `fact_ocupacion_diaria` | `fecha` (noite) | `hotel_code` | – | `room_type` |
| `fact_resenas` | `fecha_publicacion`, `fecha_estadia` | `hotel_code` | – | – |

`dim_fecha` é uma dimensão de **papel múltiplo** (*role-playing*): a mesma tabela serve para a data de check-in, a da reserva, a do cancelamento, a noite de ocupação e a data de publicação de uma avaliação. Os feriados não estão em `dim_fecha` porque dependem do país do hotel: estão em `fact_ocupacion_diaria` (a partir de `silver/calendario_hotel`).

### Dimensões

| Tabela | Granularidade (PK) | Colunas |
| --- | --- | --- |
| `dim_fecha` | um dia (`fecha`) | `fecha_key` (yyyyMMdd), `anio`, `trimestre`, `mes`, `nombre_mes`, `semana_iso`, `dia_semana`, `es_fin_de_semana`, `anio_mes`. De um ano atrás até o último check-out. |
| `dim_hotel` | `hotel_code` | `nombre`, `categoria`, `ciudad`, `pais`, `moneda`, `zona_horaria`, `habitaciones` (máximo de quartos em uma noite) |
| `dim_canal` | `channel_code` | `nombre`, `channel_type` (ota, direct, corporate, agency), `comision_pct` |
| `dim_tipo_habitacion` | `room_type` | `nombre`, `capacidad` |

### Fatos

| Tabela | Granularidade | Chaves para dimensões | Medidas |
| --- | --- | --- | --- |
| `fact_reservas` | uma reserva (`code`), sem duplicados | `hotel_code`, `channel_code`, `room_type`, `fecha_reserva`, `check_in`, `check_out` | `noches`, `habitaciones`, `huespedes`, `lead_time_dias`, `total_cop`, `comision_cop`, `neto_cop`, `penalidad_cop`; indicadores `es_cancelada`, `reembolsable`, `fx_estimada`; `rango_anticipacion`, `status`, `source` |
| `fact_cancelaciones` | uma reserva cancelada / no-show | `hotel_code`, `channel_code`, `room_type`, `check_in`, `fecha_cancelacion` | `horas_antes_checkin`, `total_cop`, `penalidad_cop`, `ingreso_perdido_cop` (total − multa); `rango_anticipacion` |
| `fact_ocupacion_diaria` | hotel × tipo de quarto × noite | `hotel_code`, `room_type`, `fecha` | `habitaciones`, `vendidas`, `limite_sobreventa`, `disponibles`, `sobrevendidas`, `reubicadas`, `habitaciones_rechazadas`, `ocupacion_pct`, `ingreso_cop`; `es_festivo`, `nombre_festivo`, `hay_evento`, `evento`, `categoria_evento` |
| `fact_resenas` | uma avaliação (só originais) | `hotel_code`, `fecha_publicacion`, `fecha_estadia` | `puntaje`, `sentimiento`, `duplicados`; `plataforma`, `idioma`, `pais_huesped` |

### Marts (um por pain do negócio)

Os marts são respostas já agregadas a partir dos fatos, então cada página do painel lê uma tabela pequena.

| Mart | Pain | Granularidade | O que entrega |
| --- | --- | --- | --- |
| `mart_p1_cancelacion` | P1 cancelamentos | canal × faixa de antecedência × reembolsável × mês de check-in | reservas, canceladas, `tasa_cancelacion`, multa e receita perdida em COP |
| `mart_p1_historico_f1` | P1 (histórico) | tipo de hotel × tipo de canal × faixa de antecedência × tipo de depósito | taxa de cancelamento da F1 2015–2017 |
| `mart_p2_sobreventa` | P2 overbooking | hotel × noite | quartos, vendidos, limite de overbooking, vendidos a mais, realocados, recusados, `% realocação` |
| `mart_p3_revenue` | P3 receita | hotel × noite | ocupação %, **ADR**, **RevPAR**, quartos em carteira 14 dias antes vs o ano anterior (**pickup %**), indicadores de feriado e evento |
| `mart_p3_precio_sugerido` | P3 preços | hotel × tipo de quarto × noite, próximas 90 noites | preço sugerido = tarifa × fator de pickup (1,10 / 0,92 quando o pickup passa de ±15 %) × fator de evento (1,15 em feriado ou evento), entre 0,75 e 1,60 da tarifa base (RN-05/RN-06), também em COP |
| `mart_p4_comisiones` | P4 custo de canal | canal × hotel × mês | receita bruta, comissão e líquida em COP, % de comissão efetiva |
| `mart_p5_reputacion` | P5 reputação | hotel × dia | nota RN-10 dos últimos 90 dias com os últimos 30 valendo o dobro, avaliações em 90 dias, % positivas, % negativas |

Além disso, `neon_cancellation_rate_by_lead` (hotel × faixa de antecedência), um arquivo JSON pequeno que `gold_neon_writeback` carrega no Neon. Veja [Conexão com o Neon](../neon-connection.mdx).

## Como o modelo é montado, em código

Tudo está em `spark_jobs/gold_modelo.py`. O job tem três passos: **ler** o silver e os catálogos do Neon, **construir** cada tabela com funções puras (sem ler nem gravar dentro delas, então podem ser testadas) e depois **verificar** e **gravar**. Os trechos são desse arquivo, cortados só onde aparece `…`.

### 1. Ler: silver e os catálogos mais recentes

```python
def run() -> dict[str, int]:
    s = spark("gold_modelo")
    silver = {name: s.read.parquet(path("silver", name))
              for name in ("reservas", "cancelaciones", "ocupacion_diaria", "calendario_hotel", "tasa_cambio_diaria")}
    silver["resenas"] = _optional(lambda: s.read.parquet(path("silver", "resenas")))
    silver["historico_f1"] = _optional(lambda: s.read.parquet(path("silver", "historico_f1")))
    dims = {name: sr._latest_dim(s, name) for name in ("hotels", "channels", "room_types")}
    dims["rates"] = _optional(lambda: sr._latest_dim(s, "rates"))
    tables = build(silver, dims, dt.datetime.now(dt.timezone.utc).date(), s)
    check(tables)
    …
```

`_optional` devolve `None` quando uma pasta ainda não existe, então uma fonte opcional ausente (avaliações, F1, tarifas) nunca para P1 a P4.

### 2. Construir: dimensões

`dim_fecha` é gerada, não lida: uma linha por dia de um ano atrás até o último check-out.

```python
def dim_fecha(first: dt.date, last: dt.date, spark: SparkSession) -> DataFrame:
    d = spark.range(1).select(F.explode(F.sequence(F.lit(first), F.lit(last))).alias("fecha"))
    dow = F.dayofweek("fecha")  # 1 = Sunday
    return (d.withColumn("fecha_key", F.date_format("fecha", "yyyyMMdd").cast("int"))
            .withColumn("anio", F.year("fecha")).withColumn("trimestre", F.quarter("fecha"))
            .withColumn("mes", F.month("fecha")).withColumn("nombre_mes", F.date_format("fecha", "MMMM"))
            .withColumn("semana_iso", F.weekofyear("fecha"))
            .withColumn("dia_semana", F.date_format("fecha", "EEEE"))
            .withColumn("es_fin_de_semana", dow.isin(1, 7))
            .withColumn("anio_mes", F.date_format("fecha", "yyyy-MM")))
```

As outras dimensões renomeiam as colunas dos catálogos do Neon. `dim_hotel` guarda cidade, país e categoria na mesma tabela (é isso que a torna estrela e não floco de neve) e adiciona o número de quartos:

```python
def dim_hotel(hotels: DataFrame, ocupacion: DataFrame) -> DataFrame:
    rooms = (ocupacion.groupBy("hotel_code", "fecha").agg(F.sum("habitaciones").alias("h"))
             .groupBy("hotel_code").agg(F.max("h").alias("habitaciones")))
    return (hotels.select(F.col("code").alias("hotel_code"), F.col("name").alias("nombre"),
                          F.col("category").alias("categoria"), F.col("city").alias("ciudad"),
                          F.col("country").alias("pais"), F.col("currency").alias("moneda"),
                          F.col("timezone").alias("zona_horaria"))
            .join(rooms, "hotel_code", "left"))
```

### 3. Construir: fatos

`fact_reservas` são as reservas do silver sem os duplicados da F4, mais a faixa de antecedência usada pelo P1:

```python
def fact_reservas(reservas: DataFrame) -> DataFrame:
    return (reservas.filter("NOT es_duplicado")
            .select("code", "source", "hotel_code", "channel_code", "channel_type", "room_type", "status",
                    "fecha_reserva", "check_in", "check_out", "noches", "habitaciones", "huespedes",
                    "lead_time_dias", "reembolsable", "es_cancelada", "currency", "fx_estimada",
                    "total_cop", "comision_pct", "comision_cop", "neto_cop", "penalidad_cop")
            .withColumn("rango_anticipacion", lead_bucket(F.col("lead_time_dias"))))
```

A receita por noite precisa de uma linha por reserva e noite de estadia. `_nights` "explode" cada reserva em suas noites, e `fact_ocupacion` adiciona essa receita e os indicadores de feriado/evento à ocupação do silver:

```python
def _nights(fact_res: DataFrame) -> DataFrame:
    night = F.explode(F.sequence("check_in", F.date_sub("check_out", 1)))
    return fact_res.filter("noches > 0").select(
        "hotel_code", "room_type", "habitaciones", "fecha_reserva", "es_cancelada",
        F.to_date(F.col("_cancelada_en")).alias("fecha_cancelacion"),
        (F.col("total_cop") / F.col("noches")).alias("ingreso_noche_cop"), night.alias("fecha"))


def fact_ocupacion(ocupacion: DataFrame, n: DataFrame, calendario: DataFrame) -> DataFrame:
    ingreso = (n.filter("NOT es_cancelada").groupBy("hotel_code", "room_type", "fecha")
               .agg(F.round(F.sum(F.col("ingreso_noche_cop") * 1.0), 2).alias("ingreso_cop")))
    cal = calendario.select("hotel_code", "fecha", "es_festivo", "nombre_festivo", "hay_evento", "evento",
                            "categoria_evento")
    return (ocupacion.join(ingreso, ["hotel_code", "room_type", "fecha"], "left")
            .join(cal, ["hotel_code", "fecha"], "left")
            .fillna({"ingreso_cop": 0.0, "es_festivo": False, "hay_evento": False}))
```

### 4. Construir: marts, prontos para análise

Um mart é um fato já agrupado no nível que uma página do painel precisa. Por exemplo o P3 (ocupação, ADR, RevPAR por hotel e noite):

```python
def mart_p3_revenue(fo: DataFrame, otb: DataFrame) -> DataFrame:
    …
    return (fo.groupBy("hotel_code", "fecha")
            .agg(F.sum("habitaciones").alias("habitaciones"), F.sum("vendidas").alias("vendidas"),
                 F.round(F.sum("ingreso_cop"), 2).alias("ingreso_cop"), …)
            .join(p, ["hotel_code", "fecha"], "left")
            .withColumn("ocupacion_pct", F.round(F.when(F.col("habitaciones") > 0,
                                                        F.col("vendidas") * 100.0 / F.col("habitaciones")), 2))
            .withColumn("adr_cop", F.round(F.when(F.col("vendidas") > 0, F.col("ingreso_cop") / F.col("vendidas")), 2))
            .withColumn("revpar_cop", F.round(F.when(F.col("habitaciones") > 0,
                                                     F.col("ingreso_cop") / F.col("habitaciones")), 2))
            .withColumn("pickup_pct", _pickup_pct()))
```

`build()` junta tudo. Os fatos usados por vários marts ficam em cache para o Spark calculá-los uma vez só:

```python
def build(silver, dims, today, spark) -> dict[str, DataFrame]:
    res, ocup, cal = silver["reservas"], silver["ocupacion_diaria"], silver["calendario_hotel"]
    fr = fact_reservas(res).cache()
    n = nights(res).cache()
    otb = on_the_books(n).cache()
    fo = fact_ocupacion(ocup, n, cal).cache()
    t = {
        "dim_fecha": dim_fecha(…), "dim_hotel": dim_hotel(dims["hotels"], ocup),
        "dim_canal": dim_canal(dims["channels"]), "dim_tipo_habitacion": dim_tipo_habitacion(dims["room_types"]),
        "fact_reservas": fr, "fact_cancelaciones": fact_cancelaciones(silver["cancelaciones"]),
        "fact_ocupacion_diaria": fo,
        "mart_p1_cancelacion": mart_p1_cancelacion(fr), "mart_p2_sobreventa": mart_p2_sobreventa(fo),
        "mart_p3_revenue": mart_p3_revenue(fo, otb), "mart_p4_comisiones": mart_p4_comisiones(fr),
        "neon_cancellation_rate_by_lead": neon_cancellation_rates(fr, today),
    }
    …
    return t
```

### 5. Verificar e depois gravar

`check()` roda antes de gravar qualquer coisa. Por exemplo, recusa reservas cujo hotel ou canal não está nas dimensões:

```python
fr = t["fact_reservas"]
orphan = fr.join(t["dim_hotel"], "hotel_code", "left_anti").count() + \
    fr.join(t["dim_canal"], "channel_code", "left_anti").count()
if orphan:
    raise quality.QualityError(f"gold.fact_reservas: {orphan} rows without their hotel or channel")
```

Só quando todas as verificações passam cada tabela é sobrescrita no S3 como Parquet. A tabela pequena para o Neon é gravada como um único arquivo JSON:

```python
for name, df in tables.items():
    if name == "neon_cancellation_rate_by_lead":
        df.coalesce(1).write.mode("overwrite").json(path("gold", name))
    else:
        df.write.mode("overwrite").parquet(path("gold", name))
```

A partir daí o Athena lê as tabelas pelo catálogo do Glue e o Power BI lê o Athena (veja [Configuração do Athena](../athena.mdx)).

## Verificações de qualidade antes de gravar

- Cada dimensão, fato e mart principal não está vazio e é único na sua chave.
- Nenhuma linha de `fact_reservas` sem seu hotel ou canal nas dimensões (sem órfãos).
- Taxas de cancelamento para o Neon entre 0 e 1.
- Preços sugeridos dentro da faixa RN-06.

Se uma verificação falha nada é gravado e o gold de ontem continua no lugar. `fact_resenas`, `mart_p5_reputacion`, `mart_p1_historico_f1` e `mart_p3_precio_sugerido` só são construídos quando suas entradas existem, então uma fonte opcional ausente nunca para P1 a P4.

## Armazenamento

Parquet em `s3://hospedaplus-lakehouse-buenavista/gold/<tabela>/`, **sem partições**: cada execução regrava a pasta inteira, então o Athena sempre lê a última execução. Registradas no Athena no banco `hospedaplus_gold` (veja [Configuração do Athena](../athena.mdx)).
