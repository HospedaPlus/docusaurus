# Conexão com o Neon

O Neon (PostgreSQL serverless, AWS us-east-2) é o banco operacional. O pipeline conversa com ele em dois sentidos: **lê** reservas, eventos e catálogos para o bronze, e **grava de volta** um resultado do gold.

<NeonFlow />

## Papéis e strings de conexão

| Variável (no `.env` dos workers) | Papel | Permissões | Usada por |
| --- | --- | --- | --- |
| `NEON_READ_URL` | `etl_reader` | Só leitura em `operation` e `streaming` | Todos os DAGs de bronze que leem o Neon |
| `NEON_WRITE_URL` | `app_writer` | Leitura e escrita | Só `gold_neon_writeback` |

As strings de conexão usam `sslmode=require` e nunca são escritas no repositório nem neste site. O código falha de propósito com uma mensagem clara se `NEON_READ_URL` estiver vazia. As leituras usam `psycopg2` e devolvem JSON Lines (`dags/hospedaplus/neon.py`); números e datas são gravados como texto para não perder nada no caminho.

### Como conectar (string de exemplo)

```bash title=".env dos workers (placeholders)"
# Role só de leitura para as extrações bronze
NEON_READ_URL=postgresql://etl_reader:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech/hospedaplus?sslmode=require
# Role de escrita para gold_neon_writeback
NEON_WRITE_URL=postgresql://app_writer:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech/hospedaplus?sslmode=require
```

```bash title="Testar"
# Conta as reservas com psql
psql "$NEON_READ_URL" -c "SELECT count(*) FROM operation.reservations;"
# O mesmo teste em Python: imprime a versão do PostgreSQL se conectar
python -c "import os, psycopg2; print(psycopg2.connect(os.environ['NEON_READ_URL']).server_version)"
```

Cada parte da string, o host com pool, o S3 e os erros comuns estão explicados em [Como conectar: Neon e S3](./how-to-connect.mdx).

### Criar o banco, os esquemas e as roles (uma vez)

Um projeto Neon novo precisa disto uma única vez. No **SQL Editor** do Neon, conectado como dono (`hospedaplus_owner`), na branch `production` do banco `hospedaplus`:

```sql
-- Esquemas: operation = motor de reservas F3, streaming = ledger F2
CREATE SCHEMA IF NOT EXISTS operation;
CREATE SCHEMA IF NOT EXISTS streaming;
-- Dois usuários com o mínimo de permissões que precisam (troque as senhas)
CREATE ROLE app_writer LOGIN PASSWORD '<writer-password>';
CREATE ROLE etl_reader LOGIN PASSWORD '<reader-password>';
-- Ninguém mais cria objetos em public
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
-- Os dois podem conectar e ver os dois esquemas
GRANT CONNECT ON DATABASE hospedaplus TO app_writer, etl_reader;
GRANT USAGE ON SCHEMA operation, streaming TO app_writer, etl_reader;
-- etl_reader nunca pode gravar, nem por engano
ALTER ROLE etl_reader SET default_transaction_read_only = on;
-- As tabelas que o seed criar depois recebem as mesmas permissões sozinhas
ALTER DEFAULT PRIVILEGES FOR ROLE hospedaplus_owner IN SCHEMA operation, streaming
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_writer;
ALTER DEFAULT PRIVILEGES FOR ROLE hospedaplus_owner IN SCHEMA operation, streaming
    GRANT USAGE, SELECT ON SEQUENCES TO app_writer;
ALTER DEFAULT PRIVILEGES FOR ROLE hospedaplus_owner IN SCHEMA operation, streaming
    GRANT SELECT ON TABLES TO etl_reader;
```

Depois, as tabelas e os primeiros dados são criados pelos repositórios das fontes, com a string do dono no `.env`:

```bash
# F3 (db_simulated): tabelas de operation, os 28 hotéis e as reservas iniciais
docker compose --profile neon run --rm --build neon-seed
# F6b (db_simulated): eventos locais em operation.local_events
docker compose --profile neon run --rm --build neon-check events
# F2 (buenavista-streaming): tabelas do ledger de streaming
docker compose run --rm neon-migrate
```

**Por que três usuários:** cada programa recebe só o que precisa. Se a string do Airflow vazar, ninguém consegue alterar uma reserva com ela.

## As três formas como o pipeline lê o Neon

### 1. Cópia incremental por hora: `bronze_neon_f2_f3`

A cada hora, para o intervalo `[início, fim)` da execução:

- linhas de `streaming.reservation_event_ledger` com `received_at` no intervalo → `bronze/f2_ledger/fecha=…/hora=HH.jsonl`
- linhas de `operation.reservations` com `updated_at` no intervalo → `bronze/f3_reservations/…`
- linhas de `operation.reservation_anomalies` criadas no intervalo → `bronze/f3_anomalies/…`

O `updated_at` é preenchido por um trigger a cada mudança, então um evento OTA atrasado, um cancelamento ou um no-show é capturado na hora em que aconteceu, mesmo que a reserva tenha sido criada dias antes. O arquivo leva o nome do intervalo, então repetir uma hora sobrescreve o mesmo arquivo.

### 2. Foto completa noturna: `bronze_neon_full_load` (03:00 UTC)

- Lê `reservations`, `reservation_anomalies`, `inventory`, `reservation_rejections` e `relocations` dentro de **uma única transação somente leitura `REPEATABLE READ`**, então todas as tabelas são do mesmo instante (o inventário bate com as reservas).
- Pagina por `id` em blocos de 50.000 linhas, então nem o Neon nem o worker seguram uma tabela inteira na memória.
- Grava arquivos `part-NNNNN.jsonl` e, só no final, um marcador `_SUCCESS`. O silver só lê fotos que têm `_SUCCESS`, então nunca usa uma foto pela metade. Partes que sobraram de uma execução anterior do mesmo dia são removidas.

Por que as duas cópias: a horária deixa o silver perto do tempo real; a foto traz o histórico criado antes do pipeline existir e corrige qualquer coisa que a cópia horária possa ter perdido.

### 3. Catálogos e eventos diários

- `bronze_neon_dims` (03:15 UTC): `hotels`, `room_types`, `channels`, `cancellation_policies` e `rates` → `bronze/neon_dims/<tabela>/fecha=….jsonl`. A tabela `guests` nunca é copiada (os dados pessoais ficam no Neon).
- `bronze_f6_events` (02:30 UTC): `operation.local_events` → `bronze/f6_events/fecha=….jsonl`.

## Write-back: `gold_neon_writeback`

Depois do gold, este DAG lê `gold/neon_cancellation_rate_by_lead/` (uma linha por hotel e faixa de antecedência `0-7`, `8-30`, `31-90`, `91+`, calculada sobre as estadias dos últimos 365 dias que já aconteceram) e faz upsert em `operation.cancellation_rate_by_lead`.

Com `NEON_REFRESH_OVERBOOKING=true` também chama `operation.refresh_overbooking_limits()`, que recalcula com essas taxas quantos quartos cada hotel pode vender além da capacidade por noite (0 em noites com um evento local de alto impacto). Fica **desligado por padrão**, porque muda o que os hotéis podem vender: é ligado de propósito.
