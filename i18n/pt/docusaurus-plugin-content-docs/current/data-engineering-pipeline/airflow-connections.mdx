# Conexões do Airflow e como são usadas

Um DAG só é útil se suas tarefas conseguem alcançar os sistemas ao redor: Neon, S3, as APIs das fontes e o broker e o banco do próprio Airflow. Esta página mostra **cada conexão que o pipeline usa, onde ela é definida e o código exato que a abre**.

## Os quatro tipos de conexão

| # | Conexão | Definida em | Formato | Usada por |
| --- | --- | --- | --- | --- |
| 1 | Infraestrutura do próprio Airflow: banco de metadados, broker do Celery, result backend | `environment:` dos arquivos Compose | URLs SQLAlchemy / AMQP | Scheduler, API server, workers |
| 2 | **Connection** do Airflow `aws_default` | Variável de ambiente `AIRFLOW_CONN_AWS_DEFAULT` (URI) | `aws://?region_name=us-east-2` | Logs remotos das tarefas em `s3://…/airflow-logs/` |
| 3 | Conexões das tarefas com o **Neon** | `NEON_READ_URL`, `NEON_WRITE_URL` no `.env` | URI PostgreSQL | DAGs bronze (leitura) e `gold_neon_writeback` (escrita) |
| 4 | Conexões das tarefas com o **S3** e as **APIs HTTP** | Role IAM da EC2 + `S3_BUCKET`, `F5_API_URL`, `NAGER_BASE_URL` | Nome do bucket / URL base | Todas as tarefas bronze, silver e gold |

## 1. As conexões do próprio Airflow (infraestrutura)

O Airflow precisa de um banco para guardar as execuções dos DAGs e de um broker para enviar tarefas aos workers do Celery. Elas são configuradas com variáveis de ambiente `AIRFLOW__<SECAO>__<CHAVE>`, que o Airflow lê no lugar do `airflow.cfg`:

```yaml title="docker-compose.workers.yaml (os workers chegam ao núcleo pelo IP privado)"
AIRFLOW__CORE__EXECUTOR: CeleryExecutor
# metadata DB (Postgres on the core EC2)
AIRFLOW__DATABASE__SQL_ALCHEMY_CONN: postgresql+psycopg2://airflow:${POSTGRES_PASSWORD}@${NUCLEO_HOST}:5432/airflow
# Celery broker (RabbitMQ on the core EC2): where the scheduler puts the tasks
AIRFLOW__CELERY__BROKER_URL: amqp://${RABBITMQ_USER}:${RABBITMQ_PASSWORD}@${NUCLEO_HOST}:5672//
# where the workers write the result of each task
AIRFLOW__CELERY__RESULT_BACKEND: db+postgresql://airflow:${POSTGRES_PASSWORD}@${NUCLEO_HOST}:5432/airflow
# Airflow 3: workers report task state to the API server
AIRFLOW__CORE__EXECUTION_API_SERVER_URL: 'http://${NUCLEO_HOST}:8080/execution/'
```

**Como funciona:** o scheduler (núcleo) coloca uma mensagem na fila RabbitMQ `bronze`, `silver` ou `gold`; o worker que escuta essa fila a pega, roda a tarefa e reporta o estado pela execution API. As portas 5432, 5672 e 8080 do núcleo estão abertas **apenas para o security group dos workers**.

## 2. A Connection do Airflow `aws_default`

Uma *Airflow Connection* é um conjunto nomeado de credenciais que os hooks do Airflow buscam pelo `conn_id`. Em vez de criá-la à mão em *Admin → Connections* (ela se perderia se o banco de metadados fosse recriado), ela é declarada como variável de ambiente `AIRFLOW_CONN_<CONN_ID>` com uma URI:

```yaml title="docker-compose.nucleo.yaml / docker-compose.workers.yaml"
AIRFLOW_CONN_AWS_DEFAULT: 'aws://?region_name=${AWS_DEFAULT_REGION:-us-east-2}'
AIRFLOW__LOGGING__REMOTE_LOGGING: 'true'
AIRFLOW__LOGGING__REMOTE_BASE_LOG_FOLDER: s3://${S3_BUCKET}/airflow-logs
AIRFLOW__LOGGING__REMOTE_LOG_CONN_ID: aws_default
```

A URI **não tem chave de acesso**: quando o provider Amazon não encontra chave, o boto3 usa a **role IAM da EC2** (`hospedaplus-pipeline-role`) e obtém credenciais temporárias. Ela é usada para os logs: uma tarefa roda na EC2 dos workers, seu log é enviado ao S3 e a UI do núcleo o lê de lá.

```bash title="Verificar a partir de qualquer contêiner do Airflow"
docker compose -f docker-compose.nucleo.yaml exec airflow-scheduler airflow connections get aws_default
docker compose -f docker-compose.nucleo.yaml exec airflow-scheduler \
  python -c "import boto3; print(boto3.client('sts').get_caller_identity()['Arn'])"   # shows the IAM role in use
```

## 3. Neon: variável de ambiente + psycopg2

Os DAGs não usam um hook do Airflow para o Neon. A string de conexão fica no `.env` dos workers e o módulo compartilhado `dags/hospedaplus/lake.py` a lê; se estiver vazia, a tarefa falha de propósito com uma mensagem clara.

```python title="dags/hospedaplus/lake.py"
def neon_url() -> str:
    url = os.getenv("NEON_READ_URL", "")
    if not url:
        raise RuntimeError("NEON_READ_URL is empty: set it in .env (role etl_reader)")
    return url
```

```python title="dags/hospedaplus/neon.py: cada leitura devolve JSON Lines"
def dump(sql: str, params: tuple = ()) -> tuple[bytes, int]:
    with psycopg2.connect(neon_url()) as conn, conn.cursor() as cur:
        cur.execute(sql, params)
        cols = [c.name for c in cur.description]
        rows = cur.fetchall()
    lines = [json.dumps(dict(zip(cols, r)), default=str, ensure_ascii=False) for r in rows]
    return ("\n".join(lines) + ("\n" if lines else "")).encode(), len(rows)
```

Só uma tarefa escreve no Neon, com outra role e outra variável:

```python title="dags/gold_neon_writeback.py"
url = os.getenv("NEON_WRITE_URL", "")          # role app_writer
with psycopg2.connect(url) as conn, conn.cursor() as cur:   # one transaction: all rows or none
    cur.executemany(UPSERT, rows)
```

```bash title=".env da EC2 dos workers (placeholders: nunca faça commit dos valores reais)"
NEON_READ_URL=postgresql://etl_reader:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech/hospedaplus?sslmode=require
NEON_WRITE_URL=postgresql://app_writer:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech/hospedaplus?sslmode=require
```

## 4. S3 e as APIs HTTP

**S3 com boto3.** Não há chave no código nem no `.env`: `boto3.client("s3")` encontra sozinho a role IAM da EC2. `S3_ENDPOINT_URL` fica vazio na AWS e só é preenchido para testes locais com MinIO.

```python title="dags/hospedaplus/lake.py"
BUCKET = os.getenv("S3_BUCKET", "hospedaplus-lakehouse")

def s3_client():
    return boto3.client("s3", endpoint_url=os.getenv("S3_ENDPOINT_URL") or None)

def put(key: str, body: bytes, content_type: str = "application/json") -> str:
    s3_client().put_object(Bucket=BUCKET, Key=key, Body=body, ContentType=content_type)
    return f"s3://{BUCKET}/{key}"
```

**S3 com Spark.** O Spark usa o protocolo `s3a://` (jars `hadoop-aws` + `aws-java-sdk-bundle` na imagem) e a mesma role IAM via `DefaultAWSCredentialsProviderChain`:

```python title="spark_jobs/session.py"
SparkSession.builder.appName(app).master("local[*]")
    .config("spark.jars", jars)
    .config("spark.hadoop.fs.s3a.impl", "org.apache.hadoop.fs.s3a.S3AFileSystem")
    .config("spark.hadoop.fs.s3a.aws.credentials.provider",
            "com.amazonaws.auth.DefaultAWSCredentialsProviderChain")

def path(layer: str, name: str) -> str:
    return f"s3a://{os.getenv('S3_BUCKET')}/{layer}/{name}"     # s3a://bucket/silver/reservas
```

**APIs HTTP com requests.** A URL base vem do `.env` e a API key opcional vai num header:

```python title="dags/bronze_f5_reviews.py"
base = os.getenv("F5_API_URL", "").rstrip("/")
headers = {"x-api-key": os.environ["F5_API_KEY"]} if os.getenv("F5_API_KEY") else {}
r = requests.get(f"{base}/api/v1/reviews", headers=headers, timeout=60,
                 params={"updated_from": data_interval_start.isoformat(), "page": page, "page_size": 100})
```

## Por que variáveis de ambiente em vez de hooks para Neon e S3

| Motivo | Detalhe |
| --- | --- |
| Um só lugar para tudo | O mesmo `.env` configura o Airflow, os DAGs e os jobs Spark; os jobs Spark rodam fora dos hooks do Airflow de qualquer forma. |
| Sobrevive a uma reconstrução | Nada fica guardado no banco de metadados, então recriar o Postgres não perde nenhuma conexão. |
| Mesmo código no CI | Os testes rodam o código dos DAGs com variáveis falsas, sem precisar da UI do Airflow. |
| Nenhuma chave AWS | O acesso ao S3 vem da role IAM; não há nada para rotacionar ou vazar. |

## O mesmo com hooks do Airflow (opcional)

Os providers Amazon e Postgres já estão instalados (`apache-airflow-providers-amazon==9.16.0`, `apache-airflow-providers-postgres==6.4.0`), então o projeto pode passar a usar hooks sem mudar a imagem. Declare a conexão como URI:

```bash title=".env (exemplo, placeholders)"
AIRFLOW_CONN_NEON_READER='postgresql://etl_reader:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech:5432/hospedaplus?sslmode=require'
```

```python title="Uma tarefa que usa os hooks"
from airflow.providers.postgres.hooks.postgres import PostgresHook
from airflow.providers.amazon.aws.hooks.s3 import S3Hook

@task(queue="bronze")
def copy_hotels():
    rows = PostgresHook(postgres_conn_id="neon_reader").get_records("SELECT * FROM operation.hotels")
    body = "\n".join(json.dumps(r, default=str) for r in rows)
    S3Hook(aws_conn_id="aws_default").load_string(body, key="bronze/neon_dims/hotels/test.jsonl",
                                                  bucket_name="hospedaplus-lakehouse-buenavista", replace=True)
```

As duas abordagens abrem as mesmas conexões; o projeto usa variáveis de ambiente pelos motivos acima.

## Conectar DAGs entre si: Assets

Os DAGs também se "conectam" entre si, sem horários fixos, por meio de **Assets** (Airflow 3). Uma tarefa declara o que escreve com `outlets=` e um DAG declara o que espera com `schedule=`:

```python title="dags/hospedaplus/lake.py + dags/silver_reservas_daily.py"
BRONZE_F3_RESERVATIONS = Asset("s3://hospedaplus-lakehouse/bronze/f3_reservations")

@task(queue="bronze", outlets=[BRONZE_F3_RESERVATIONS])      # bronze: "I updated this"
def f3_reservations(...): ...

@dag(schedule=((SILVER_FX_DAILY & BRONZE_F3_FULL & BRONZE_NEON_DIMS) | BRONZE_F3_RESERVATIONS))
def silver_reservas_daily(): ...                              # silver: runs when its inputs change
```

`&` espera todos os assets, `|` roda quando qualquer um muda. Veja [DAGs](./dags.mdx) e [Como conectar ao Neon e ao S3](./how-to-connect.mdx).
