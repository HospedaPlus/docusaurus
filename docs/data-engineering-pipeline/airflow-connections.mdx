# Airflow connections and how they are used

A DAG is only useful if its tasks can reach the systems around them: Neon, S3, the source APIs, and Airflow's own broker and database. This page shows **every connection the pipeline uses, where it is defined and the exact code that opens it**.

<ConnectionsFlow />

## The four kinds of connections

| # | Connection | Defined in | Format | Used by |
| --- | --- | --- | --- | --- |
| 1 | Airflow's own infrastructure: metadata DB, Celery broker, result backend | `environment:` of the Compose files | SQLAlchemy / AMQP URLs | Scheduler, API server, workers |
| 2 | Airflow **Connection** `aws_default` | Env var `AIRFLOW_CONN_AWS_DEFAULT` (URI) | `aws://?region_name=us-east-2` | Remote task logs in `s3://…/airflow-logs/` |
| 3 | Task connections to **Neon** | `NEON_READ_URL`, `NEON_WRITE_URL` in `.env` | PostgreSQL URI | Bronze DAGs (read) and `gold_neon_writeback` (write) |
| 4 | Task connections to **S3** and **HTTP APIs** | IAM role of the EC2 + `S3_BUCKET`, `F5_API_URL`, `NAGER_BASE_URL` | Bucket name / base URL | Every bronze, silver and gold task |

## 1. Airflow's own connections (infrastructure)

Airflow itself needs a database to store DAG runs and a broker to send tasks to the Celery workers. They are set with `AIRFLOW__<SECTION>__<KEY>` environment variables, which Airflow reads instead of `airflow.cfg`:

```yaml title="docker-compose.workers.yaml (the workers reach the core by its private IP)"
AIRFLOW__CORE__EXECUTOR: CeleryExecutor
# metadata DB (Postgres on the core EC2)
AIRFLOW__DATABASE__SQL_ALCHEMY_CONN: postgresql+psycopg2://airflow:${POSTGRES_PASSWORD}@${NUCLEO_HOST}:5432/airflow
# Celery broker (RabbitMQ on the core EC2): where the scheduler puts the tasks
AIRFLOW__CELERY__BROKER_URL: amqp://${RABBITMQ_USER}:${RABBITMQ_PASSWORD}@${NUCLEO_HOST}:5672//
# where the workers write the result of each task
AIRFLOW__CELERY__RESULT_BACKEND: db+postgresql://airflow:${POSTGRES_PASSWORD}@${NUCLEO_HOST}:5432/airflow
# Airflow 3: workers report task state to the API server
AIRFLOW__CORE__EXECUTION_API_SERVER_URL: 'http://${NUCLEO_HOST}:8080/execution/'
```

**How it works:** the scheduler (core) puts a message in the RabbitMQ queue `bronze`, `silver` or `gold`; the worker listening to that queue takes it, runs the task and reports the state through the execution API. Ports 5432, 5672 and 8080 of the core are open **only to the workers' security group**.

## 2. The Airflow Connection `aws_default`

An *Airflow Connection* is a named set of credentials that Airflow hooks look up by its `conn_id`. Instead of creating it by hand in *Admin → Connections* (it would be lost if the metadata DB is recreated), it is declared as an environment variable `AIRFLOW_CONN_<CONN_ID>` with a URI:

```yaml title="docker-compose.nucleo.yaml / docker-compose.workers.yaml"
AIRFLOW_CONN_AWS_DEFAULT: 'aws://?region_name=${AWS_DEFAULT_REGION:-us-east-2}'
AIRFLOW__LOGGING__REMOTE_LOGGING: 'true'
AIRFLOW__LOGGING__REMOTE_BASE_LOG_FOLDER: s3://${S3_BUCKET}/airflow-logs
AIRFLOW__LOGGING__REMOTE_LOG_CONN_ID: aws_default
```

The URI has **no access key**: when the Amazon provider finds no key, boto3 uses the **IAM role of the EC2** (`hospedaplus-pipeline-role`) and gets temporary credentials. It is used for logs: a task runs on the workers EC2, its log is uploaded to S3, and the UI on the core reads it from there.

```bash title="Check it from any Airflow container"
docker compose -f docker-compose.nucleo.yaml exec airflow-scheduler airflow connections get aws_default
docker compose -f docker-compose.nucleo.yaml exec airflow-scheduler \
  python -c "import boto3; print(boto3.client('sts').get_caller_identity()['Arn'])"   # shows the IAM role in use
```

## 3. Neon: environment variable + psycopg2

The DAGs do not use an Airflow hook for Neon. The connection string lives in the `.env` of the workers and the shared module `dags/hospedaplus/lake.py` reads it; if it is empty the task fails on purpose with a clear message.

```python title="dags/hospedaplus/lake.py"
def neon_url() -> str:
    url = os.getenv("NEON_READ_URL", "")
    if not url:
        raise RuntimeError("NEON_READ_URL is empty: set it in .env (role etl_reader)")
    return url
```

```python title="dags/hospedaplus/neon.py: every read returns JSON Lines"
def dump(sql: str, params: tuple = ()) -> tuple[bytes, int]:
    with psycopg2.connect(neon_url()) as conn, conn.cursor() as cur:
        cur.execute(sql, params)
        cols = [c.name for c in cur.description]
        rows = cur.fetchall()
    lines = [json.dumps(dict(zip(cols, r)), default=str, ensure_ascii=False) for r in rows]
    return ("\n".join(lines) + ("\n" if lines else "")).encode(), len(rows)
```

Only one task writes to Neon, with a different role and variable:

```python title="dags/gold_neon_writeback.py"
url = os.getenv("NEON_WRITE_URL", "")          # role app_writer
with psycopg2.connect(url) as conn, conn.cursor() as cur:   # one transaction: all rows or none
    cur.executemany(UPSERT, rows)
```

```bash title=".env of the workers EC2 (placeholders: never commit the real values)"
NEON_READ_URL=postgresql://etl_reader:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech/hospedaplus?sslmode=require
NEON_WRITE_URL=postgresql://app_writer:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech/hospedaplus?sslmode=require
```

## 4. S3 and the HTTP APIs

**S3 with boto3.** There is no key in the code or in `.env`: `boto3.client("s3")` finds the IAM role of the EC2 by itself. `S3_ENDPOINT_URL` is empty on AWS and only set for local tests with MinIO.

```python title="dags/hospedaplus/lake.py"
BUCKET = os.getenv("S3_BUCKET", "hospedaplus-lakehouse")

def s3_client():
    return boto3.client("s3", endpoint_url=os.getenv("S3_ENDPOINT_URL") or None)

def put(key: str, body: bytes, content_type: str = "application/json") -> str:
    s3_client().put_object(Bucket=BUCKET, Key=key, Body=body, ContentType=content_type)
    return f"s3://{BUCKET}/{key}"
```

**S3 with Spark.** Spark uses the `s3a://` protocol (jars `hadoop-aws` + `aws-java-sdk-bundle` in the image) and the same IAM role through `DefaultAWSCredentialsProviderChain`:

```python title="spark_jobs/session.py"
SparkSession.builder.appName(app).master("local[*]")
    .config("spark.jars", jars)
    .config("spark.hadoop.fs.s3a.impl", "org.apache.hadoop.fs.s3a.S3AFileSystem")
    .config("spark.hadoop.fs.s3a.aws.credentials.provider",
            "com.amazonaws.auth.DefaultAWSCredentialsProviderChain")

def path(layer: str, name: str) -> str:
    return f"s3a://{os.getenv('S3_BUCKET')}/{layer}/{name}"     # s3a://bucket/silver/reservas
```

**HTTP APIs with requests.** The base URL comes from `.env`, the optional API key goes in a header:

```python title="dags/bronze_f5_reviews.py"
base = os.getenv("F5_API_URL", "").rstrip("/")
headers = {"x-api-key": os.environ["F5_API_KEY"]} if os.getenv("F5_API_KEY") else {}
r = requests.get(f"{base}/api/v1/reviews", headers=headers, timeout=60,
                 params={"updated_from": data_interval_start.isoformat(), "page": page, "page_size": 100})
```

## Why environment variables instead of hooks for Neon and S3

| Reason | Detail |
| --- | --- |
| One place for everything | The same `.env` configures Airflow, the DAGs and the Spark jobs; Spark jobs run outside Airflow hooks anyway. |
| Survives a rebuild | Nothing is stored in the metadata DB, so recreating Postgres does not lose any connection. |
| Same code in CI | The tests run the DAG code with fake variables, no Airflow UI needed. |
| No AWS keys at all | S3 access comes from the IAM role; there is nothing to rotate or leak. |

## The same thing with Airflow hooks (optional)

The Amazon and Postgres providers are already installed (`apache-airflow-providers-amazon==9.16.0`, `apache-airflow-providers-postgres==6.4.0`), so the project can switch to hooks without changing the image. Declare the connection as a URI:

```bash title=".env (example, placeholders)"
AIRFLOW_CONN_NEON_READER='postgresql://etl_reader:<password>@ep-<endpoint-id>.us-east-2.aws.neon.tech:5432/hospedaplus?sslmode=require'
```

```python title="A task that uses the hooks"
from airflow.providers.postgres.hooks.postgres import PostgresHook
from airflow.providers.amazon.aws.hooks.s3 import S3Hook

@task(queue="bronze")
def copy_hotels():
    rows = PostgresHook(postgres_conn_id="neon_reader").get_records("SELECT * FROM operation.hotels")
    body = "\n".join(json.dumps(r, default=str) for r in rows)
    S3Hook(aws_conn_id="aws_default").load_string(body, key="bronze/neon_dims/hotels/test.jsonl",
                                                  bucket_name="hospedaplus-lakehouse-buenavista", replace=True)
```

Both approaches open the same connections; the project uses environment variables for the reasons above.

## Connecting DAGs to each other: Assets

DAGs are also "connected" between them, without fixed times, through **Assets** (Airflow 3). A task declares what it writes with `outlets=`, and a DAG declares what it waits for with `schedule=`:

```python title="dags/hospedaplus/lake.py + dags/silver_reservas_daily.py"
BRONZE_F3_RESERVATIONS = Asset("s3://hospedaplus-lakehouse/bronze/f3_reservations")

@task(queue="bronze", outlets=[BRONZE_F3_RESERVATIONS])      # bronze: "I updated this"
def f3_reservations(...): ...

@dag(schedule=((SILVER_FX_DAILY & BRONZE_F3_FULL & BRONZE_NEON_DIMS) | BRONZE_F3_RESERVATIONS))
def silver_reservas_daily(): ...                              # silver: runs when its inputs change
```

`&` waits for all the assets, `|` runs when any of them changes. See [DAGs](./dags.mdx) and [How to connect to Neon and S3](./how-to-connect.mdx).
