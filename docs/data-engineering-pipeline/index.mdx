# Data Engineering Pipeline

The pipeline takes the seven sources (F1 to F7) from where they first land, Neon or S3, and turns them into a small set of clean, business-ready tables that Athena and Power BI read. It runs on **Apache Airflow 3** with **Celery** workers and **Apache Spark**, and stores everything in an **S3 lakehouse** organised in three layers: **Bronze**, **Silver** and **Gold** (the medallion architecture).

Source code: [HospedaPlus/hospedaplus-pipeline](https://github.com/HospedaPlus/hospedaplus-pipeline).

## The pipeline from start to end

<PipelineFlow />

Step by step, this is what happens every day:

1. **The sources produce data all the time.** F2, F3 and F4 write bookings into Neon through the same function, `operation.reservar()`. F5 publishes reviews in its API every 15 minutes. F6 and F7 are public APIs. F1 is a fixed CSV. See [Data sources](../data-sources.mdx).
2. **Bronze copies everything to S3 as it arrived.** Every hour Airflow copies from Neon the bookings and events that changed in the last hour, and pulls the new reviews from the F5 API. Once a night it takes a full, consistent snapshot of Neon and a copy of the catalogs (hotels, room types, channels, rates). Once a day it downloads the exchange rates, and once a month the public holidays. Nothing is changed: bronze is the raw, replayable record.
3. **Silver cleans and conforms with Spark.** As soon as its bronze inputs are fresh, each silver DAG starts by itself. It keeps the newest version of every booking or review, removes duplicates, converts every amount to **COP**, adds commissions, lead time and cancellation timing, and checks the data before writing Parquet.
4. **Gold builds the analytical model.** When the four silver tables of the night are ready (around 03:35 UTC, 22:35 in Colombia), `gold_modelo_daily` rebuilds a **star schema** (4 dimensions, 4 facts) plus one mart per business question (P1 to P5), including a suggested nightly price.
5. **Gold feeds the operation back.** `gold_neon_writeback` writes the cancellation rate per hotel and lead time into Neon, so the operation uses the same numbers the business sees.
6. **Athena exposes the tables, Power BI reads them.** Silver and gold tables are registered in the Glue Data Catalog through Athena DDL, and Power BI queries them through Athena. The dashboards are fresh before 06:00 local time in every hotel.

## Why a lakehouse

Yes: the storage is a **lakehouse**. The data lives as open files (JSON in bronze, Parquet in silver and gold) in **one S3 bucket**, like a data lake, but it is used like a warehouse: every table has a fixed schema, is checked before it is written, is registered in the **Glue Data Catalog** and is queried with **SQL in Athena** by Power BI. There is no separate warehouse database to copy into.

| Need | Data lake alone | Warehouse alone | Lakehouse (what we use) |
| --- | --- | --- | --- |
| Keep raw data of every format (JSON, CSV, Excel) to replay it | ✅ | ❌ | ✅ bronze |
| Typed tables, quality rules, SQL for BI | ❌ | ✅ | ✅ silver / gold + Athena |
| Pay only for storage and per query, no server running | ✅ | ❌ (cluster always on) | ✅ S3 + Athena serverless |
| One copy of the data, no ETL into a second database | – | ❌ | ✅ |
| Spark and SQL read the same files | – | – | ✅ |

**Why it fits HospedaPlus:** the sources are very different (database rows, API JSON, agency Excel files, a Kaggle CSV), the volume is small enough for Spark in local mode, the budget is a student AWS account, and the business only needs a few dashboards that read aggregated tables. A lakehouse keeps the raw history cheaply and still gives Power BI clean, typed tables.

## ETL, OLTP and OLAP: where each step happens

The platform keeps two worlds apart: the **operational (OLTP)** side, where bookings are written one by one, and the **analytical (OLAP)** side, where the business reads aggregated, ready-to-use tables. The pipeline is the ETL that connects them.

| Stage | What it is here | Where it runs | Where it writes |
| --- | --- | --- | --- |
| **OLTP** | Neon (PostgreSQL): schemas `operation` and `streaming`. Every booking from F2 (OTA), F3 (own engine) and F4 (agencies) lands here through `operation.reservar()`, with inventory and overbooking control; F6 local events too. Small, frequent, transactional writes. | Neon, AWS us-east-2 | Neon |
| **E · Extract** | Bronze DAGs read Neon (role `etl_reader`), the F5 and F6/F7 APIs and the F1/F4 files, and copy them **as they are**. | Celery worker `bronze` (workers EC2), plain Python | S3 `bronze/` |
| **T · Transform** | Spark jobs clean, deduplicate, convert to COP, join catalogs and check quality (silver), then model the star schema and the marts (gold). | Celery workers `silver` and `gold` (workers EC2), Spark local mode | S3 `silver/` and `gold/` (Parquet) |
| **L · Load** | Gold is written as Parquet and registered in the Glue Data Catalog; one result (cancellation rates) is also loaded back into Neon. | Worker `gold`; Athena DDL | S3 `gold/` + Glue Catalog; Neon `operation.cancellation_rate_by_lead` |
| **OLAP** | The gold layer: star schema (`dim_*`, `fact_*`) and marts P1–P5, ready for analysis. Read-only, wide scans, aggregated. | Athena (serverless SQL) | Read by Power BI |

Airflow (core EC2) does not move data itself: it only **orchestrates**, deciding when each step runs and on which worker.

## Where it runs

| Machine | What runs there | Why |
| --- | --- | --- |
| **Core** EC2 (t3.medium) | Airflow API server and UI, scheduler, DAG processor, triggerer, Postgres (Airflow metadata), RabbitMQ (Celery broker), Flower, Nginx | Light, always-on control plane. Public UIs behind Nginx and Cloudflare. |
| **Workers** EC2 (t3.xlarge) | Three Celery workers, one per queue: `bronze`, `silver`, `gold`. Spark runs in local mode inside the worker that runs the task. | The heavy Spark work stays off the scheduler machine, and each layer has its own worker so a long gold job never blocks the hourly bronze copy. |
| **Neon** (us-east-2) | Operational PostgreSQL: `operation` and `streaming` schemas | Source of F2, F3, F4 bookings and F6 events; receives the gold write-back. |
| **S3** `hospedaplus-lakehouse-buenavista` (us-east-2) | `bronze/`, `silver/`, `gold/`, `athena-results/` | The lakehouse. |

Each task picks its worker with `queue="bronze" | "silver" | "gold"`. The Airflow UI is at `airflow-buenavista.coderhivex.com`, Flower at `flower-buenavista.coderhivex.com`.
