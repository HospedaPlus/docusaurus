# <SourceTitleIcon icon="database" tone="teal" />F3 · Own booking engine <SourceType>PostgreSQL database</SourceType>

Simulated operational database of the chain's own booking engine. It holds the hotel catalog, the room inventory, the seasonal rates and the direct and corporate bookings. It is also where the bookings of every other channel (F2 OTAs, F4 agencies) end up, through one booking function.

## How it is simulated

Two jobs, both with the image of the repository:

1. **Seed** (`python -m seed all`). Loads the catalog, 365 nights of inventory and rates ahead, 60,000+ guests and the booking history (`dev`: 90 past nights, `full`: 400). City hotels get more arrivals from Sunday to Tuesday, resorts on weekends, high season brings more guests, and future occupancy falls the further ahead you look, as in a real booking curve. Same seed + same start date = the same data, row for row.
2. **Simulator** (`python -m seed simulate`). Runs all the time on AWS EC2. Every minute it books a direct or corporate stay through `operation.reservar()` (`rejected` when the hotel is full), now and then cancels one through `operation.cancelar()`, keeps injecting bad rows, and once a day puts a new night on sale 365 days ahead.

### Frequency and volume

- `SIM_BOOKINGS_PER_MIN=1` (set this way on the EC2): about 1,440 booking attempts a day, so F3 is a continuous source and the pipeline always finds new rows.
- `SEED_MODE=full` loads the full history; `dev` is a small version for development.
- `python -m seed check` runs 24 health and integrity checks and passes only if all of them pass (counts, catalog, no orphans, inventory = confirmed bookings, no booking before the day it was made).

## Where it is stored

```text
seed + simulator ─► Neon operation ◄─ F2 consumer and F4 loader (same reservar())
Neon ─► Airflow bronze_neon_f2_f3 (every hour, by updated_at) ─► S3 bronze/f3_reservations/, f3_anomalies/
Neon ─► Airflow bronze_neon_full_load (nightly snapshot)    ─► S3 bronze/f3_*_full/
Neon ─► Airflow bronze_neon_dims (nightly catalog)           ─► S3 bronze/neon_dims/
```

Neon is the operational store. The lake gets F3 two ways: every hour, the rows changed since the last run (`reservations.updated_at` is set by a trigger on every change), and every night a full snapshot of reservations, anomalies, inventory, relocations and rejections, taken in one transaction and marked with `_SUCCESS`. The `guests` table is never copied: personal data stays in Neon.

## How to access it

| Property | Value |
| --- | --- |
| Host | Neon endpoint of the `production` branch (pooled host with `-pooler` for clients, direct host for the seed) |
| Port | `5432` |
| Database | `hospedaplus` |
| SSL | `sslmode=require` |

Each client uses its own role. Ask the team for the connection strings: they are never written in the repository or in this site.

| Role | Used by | Can |
| --- | --- | --- |
| `hospedaplus_owner` | Seed and migrations | Everything. |
| `app_writer` | F2 consumer, F3 simulator, F4 loader, pipeline write-back | Read and write data; no schema changes. |
| `etl_reader` | Airflow bronze worker, team (DBeaver, psql) | Read only. |

## What it contains

| Table | Content |
| --- | --- |
| `hotels`, `room_types`, `rooms` | 28 hotels (`HP-CO-001`…) with time zone and currency; `SINGLE`, `DOUBLE`, `TWIN`, `SUITE`; 4,000 rooms. |
| `channels` | 21 sales channels with their commission (RN-02). |
| `rates` | Price per night by hotel, room type and season (RN-05). |
| `inventory` | Rooms total, sold and overbooking limit by hotel, room type and night (RN-03). |
| `guests` | Guests `G-0000001`…, with the same `guest_ref` and loyalty tier as F2 (personal data, RN-11). |
| `reservations` | Bookings of every channel, with cancellations, no-shows and penalties. |
| `reservation_anomalies` | Rows with known data quality issues, kept apart on purpose. |
| `reservation_rejections`, `relocations` | Bookings refused for lack of rooms (RN-04), relocated bookings. |
| `cancellation_policies`, `cancellation_rate_by_lead` | Policies by channel (RN-07); cancellation rates written back by the pipeline. |
| `local_events` | The F6 local events. |

<AccessNote icon="alert" title="Known data quality issues">

Rows that would break the constraints go to `reservation_anomalies` (2% each by default, `SEED_ZERO_GUESTS_RATE` and `SEED_INVALID_DATES_RATE`), both in the seed and in the continuous simulator:

- Bookings with zero guests.
- Check-out dates earlier than the check-in date.

</AccessNote>
