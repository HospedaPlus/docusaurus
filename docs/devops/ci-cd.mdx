# CI/CD of each repository

Every HospedaPlus repository uses **GitHub Actions**. The idea is the same everywhere:

1. **CI (Continuous Integration)** runs on every Pull Request: it checks style, runs the tests and builds the Docker image *without publishing it*. If something fails, the PR shows a red ❌ and is not merged.
2. **CD (Continuous Delivery/Deployment)** runs when the change reaches `main`: it publishes a **versioned image** and **deploys** it on AWS.
3. The deploy is **off until its secrets exist**: if a secret is missing the job ends in green with a notice (`Deploy skipped`) instead of failing.

### Words used on this page

| Term | Meaning |
| --- | --- |
| **Workflow** | A YAML file in `.github/workflows/`. GitHub runs it when its `on:` event happens. |
| **Job** | A group of steps that runs on a fresh Linux machine (`runs-on: ubuntu-latest`). Jobs run in parallel unless one says `needs:`. |
| **GHCR** | GitHub Container Registry, `ghcr.io/hospedaplus/<repo>`: where the images are stored, next to the code. |
| **Secret** | A value stored encrypted in *Settings → Secrets and variables → Actions* (SSH key, host). It never appears in the logs. |
| **Environment `production`** | A GitHub environment: it groups the deploy secrets and shows the deployment history. |

## 1. hospedaplus-pipeline (CI/CD II: data engineering)

One file, `.github/workflows/ci-cd.yml`, with four jobs chained with `needs:`: **lint → test → image → deploy**.

```yaml title=".github/workflows/ci-cd.yml (triggers)"
on:
  pull_request:
    branches: [main]      # every PR: lint + tests + image build (not published)
  push:
    branches: [main]      # merge: the same, then publish and deploy
    tags: ["v*"]          # tag v1.2.3: the image also gets the version as tag
  workflow_dispatch:      # "Run workflow" button

concurrency:
  group: ci-cd-${{ github.ref }}
  cancel-in-progress: true   # a new push cancels the old run of the same branch
```

**Lint** checks Python style with ruff and that the three Compose files are valid (a typo in YAML fails here, not on the server):

```yaml
  lint:
    steps:
      - uses: astral-sh/ruff-action@v3
        with:
          version: "0.14.3"
          args: check dags spark_jobs tests
      - name: Compose files are valid
        run: |
          cp .env.example .env
          docker compose -f docker-compose.yaml config -q
          docker compose -f docker-compose.nucleo.yaml config -q
          docker compose -f docker-compose.workers.yaml config -q
```

**Test** installs Airflow exactly like the Docker image does and runs pytest: every DAG must import without errors (DagBag), the Spark jobs run on small sample data, and the data-quality checks of `spark_jobs/quality.py` are tested. Java 17 is installed because Spark needs it.

```yaml
  test:
    env:
      AIRFLOW_HOME: ${{ github.workspace }}/.airflow-ci
    steps:
      - uses: actions/setup-python@v5
        with: {python-version: "3.12"}
      - uses: actions/setup-java@v4
        with: {distribution: temurin, java-version: "17"}
      - uses: astral-sh/setup-uv@v6
        with: {activate-environment: true}
      - name: Install Airflow + requirements (same pins as the image)
        run: scripts/ci-install.sh pytest==8.4.2
      - name: DAG validation, Spark jobs and data quality tests
        run: python -m pytest -v -p no:logging
```

`scripts/ci-install.sh` solves a real problem: Airflow is installed with its official *constraints* file, but our own pins in `requirements.txt` must win. Without it, uv upgraded SQLAlchemy to 2.x and broke Airflow.

```bash title="scripts/ci-install.sh"
AIRFLOW_VERSION=3.1.5
PY=$(python -c 'import sys; print(f"{sys.version_info.major}.{sys.version_info.minor}")')
curl -fsSL "https://raw.githubusercontent.com/apache/airflow/constraints-${AIRFLOW_VERSION}/constraints-${PY}.txt" \
  -o /tmp/constraints.txt
# Drop from the constraints every package we pin ourselves
names=$(grep -vE '^\s*(#|$)' requirements.txt | sed -E 's/[=<>!~ ].*//' | paste -sd'|')
grep -viE "^(${names}|botocore|s3transfer|py4j)==" /tmp/constraints.txt > /tmp/constraints-ci.txt
uv pip install "apache-airflow==${AIRFLOW_VERSION}" -r requirements.txt -c /tmp/constraints-ci.txt "$@"
```

**Image** builds the Dockerfile and, outside PRs, publishes it to GHCR with three kinds of tags: the short commit SHA (`3f2a1bc`), the branch (`main`) and the version (`1.2.3` when a `v1.2.3` tag is pushed). The build cache lives in GitHub Actions (`type=gha`), so a build where only DAGs changed takes seconds.

```yaml
  image:
    needs: [lint, test]
    permissions: {contents: read, packages: write}
    steps:
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha,prefix=,format=short
            type=ref,event=branch
            type=semver,pattern={{version}}
      - uses: docker/build-push-action@v6
        with:
          push: ${{ github.event_name != 'pull_request' }}   # PRs only build
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

**Deploy** connects by SSH to the two EC2 machines. First the **core** (Airflow + RabbitMQ), then the **workers**, so the workers always find the new scheduler. Each machine pulls `main` and recreates only the containers that changed.

```yaml
  deploy:
    needs: image
    if: github.event_name != 'pull_request'
    environment: production
    env:
      SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
      NUCLEO_HOST: ${{ secrets.NUCLEO_HOST }}
      WORKERS_HOST: ${{ secrets.WORKERS_HOST }}
      SSH_USER: ${{ secrets.DEPLOY_SSH_USER || 'ubuntu' }}
    steps:
      - name: Deploy is off until the secrets exist
        id: gate
        run: |
          if [ -z "$SSH_KEY" ] || [ -z "$NUCLEO_HOST" ] || [ -z "$WORKERS_HOST" ]; then
            echo "::notice::Deploy skipped: add DEPLOY_SSH_KEY, NUCLEO_HOST and WORKERS_HOST to turn it on."
            echo "enabled=false" >> "$GITHUB_OUTPUT"
          else
            echo "enabled=true" >> "$GITHUB_OUTPUT"
          fi
      - if: steps.gate.outputs.enabled == 'true'
        name: Núcleo (Airflow + RabbitMQ), then workers
        run: |
          run() { ssh -i ~/.ssh/deploy -o StrictHostKeyChecking=accept-new "$SSH_USER@$1" "$2"; }
          run "$NUCLEO_HOST"  'cd ~/hospedaplus-pipeline && git pull --ff-only && docker compose -f docker-compose.nucleo.yaml up -d --build'
          run "$WORKERS_HOST" 'cd ~/hospedaplus-pipeline && git pull --ff-only && docker compose -f docker-compose.workers.yaml up -d --build && docker compose -f docker-compose.workers.yaml restart'
```

## 2. buenavista-streaming (F2), db_simulated (F3) and hospedaplus-csv (F4): CI/CD I

The three source simulators share the same `cd.yml` (lint → image → deploy to the **EC2 sources** machine). F2 and F3 also have a `ci.yml` that runs their tests.

### buenavista-streaming (F2 Kafka)

```yaml title=".github/workflows/ci.yml"
on:
  pull_request:
  push:
    branches: [main, develop]
jobs:
  test:
    steps:
      - uses: actions/setup-python@v5
        with: {python-version: "3.12", cache: pip}
      - run: python -m pip install -e ".[dev]"
      - run: ruff check .             # lint
      - run: ruff format --check .    # formatting
      - run: pytest                   # events, Kafka producer/consumer, Neon sinks
```

```yaml title=".github/workflows/cd.yml (deploy step)"
      - if: steps.gate.outputs.enabled == 'true'
        name: Update the EC2 sources
        run: |
          ssh -i ~/.ssh/deploy "$SSH_USER@$HOST" \
            'cd ~/buenavista-streaming && git pull --ff-only && docker compose up -d --build'
```

`docker compose up -d --build` recreates `producer` and `neon-consumer` with the new code; Kafka keeps running and keeps its data (volume `kafka_data`), so no event is lost during the deploy.

### db_simulated (F3 booking engine)

The CI starts a throw-away **PostgreSQL 16** next to the job, so the tests run against a real database: `reservar()`, 50 concurrent buyers for the last room, penalties, etc.

```yaml title=".github/workflows/ci.yml"
jobs:
  test:
    services:
      postgres:
        image: postgres:16-alpine
        env: {POSTGRES_USER: hospedaplus, POSTGRES_PASSWORD: hospedaplus, POSTGRES_DB: hospedaplus_test}
        ports: ["5432:5432"]
        options: --health-cmd "pg_isready -U hospedaplus" --health-interval 5s --health-retries 10
    env:
      TEST_DATABASE_URL: postgresql://hospedaplus:hospedaplus@localhost:5432/hospedaplus_test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: "3.12"}
      - run: pip install -e ".[test]"
      - run: pytest -v
```

The deploy is smarter than a plain restart: it compares the commit before and after `git pull` and only touches Neon when the SQL or the local events changed.

```bash title="cd.yml: what runs on the EC2 sources"
cd ~/db_simulated && OLD=$(git rev-parse HEAD) && git pull --ff-only
if ! git diff --quiet "$OLD" HEAD -- sql/; then          # schema/functions changed
  docker compose --profile neon run --rm neon-check init  # applies it (init never deletes data)
fi
docker compose --profile neon up -d --build neon-simulator
if ! git diff --quiet "$OLD" HEAD -- data/local_events.csv; then
  docker compose --profile neon run --rm neon-check events   # reloads F6b local events
fi
```

### hospedaplus-csv (F4 agencies)

Only `cd.yml`: ruff lint, image build and deploy of the single service `f4-weekly`.

```bash title="cd.yml: what runs on the EC2 sources"
cd ~/hospedaplus-csv && git pull --ff-only && docker compose up -d --build f4-weekly
```

## 3. api-reviews (F5): the most complete pipeline

`ci.yml` has five jobs. The last one, **CI passed**, is the single required check for branch protection: it is green only if all the others are.

| Job | What it guarantees |
| --- | --- |
| **Lint and format** | `uv sync --frozen` (exact versions of `uv.lock`), `ruff check`, `ruff format --check` |
| **Secret scan** | `gitleaks` reads the *whole* git history and fails if a password or key was ever committed |
| **Tests (PostgreSQL)** | Alembic `upgrade → downgrade → upgrade`, `alembic check` (models = migrations), pytest with **≥ 90 % coverage**, and the seed is idempotent (a second run inserts 0 rows) and reproducible (same digest) |
| **Docker build and smoke test** | Builds the image, starts it against a PostgreSQL service, waits for `/health/ready`, runs the seed inside the image, calls the API and checks the container runs as the non-root user `app` |
| **CI passed** | Fails if any job above did not succeed |

```yaml title="ci.yml: the seed must be idempotent and reproducible"
      - name: Seed is idempotent and reproducible
        run: |
          count()  { psql "$DATABASE_URL" -tAc "SELECT count(*) FROM reviews"; }
          digest() { psql "$DATABASE_URL" -tAc "SELECT md5(string_agg(platform || external_id || rating || text, ',' ORDER BY platform, external_id)) FROM reviews"; }
          uv run python -m src.seed --mode dev
          first_count=$(count); first_digest=$(digest)
          uv run python -m src.seed --mode dev
          [ "$(count)" = "$first_count" ] || { echo "::error::Second seed run inserted rows"; exit 1; }
```

`cd.yml` starts **only after CI finished green on `main`** (`workflow_run`) and deploys exactly the commit CI tested. It logs in to AWS with **OIDC**: GitHub gets a temporary token for an IAM role, so no AWS access key is stored anywhere.

```yaml title=".github/workflows/cd.yml"
on:
  workflow_run:
    workflows: [CI]
    types: [completed]
    branches: [main]
permissions:
  id-token: write                 # GitHub OIDC -> AWS IAM role
jobs:
  deploy:
    if: vars.AWS_ROLE_ARN != '' && github.event.workflow_run.conclusion == 'success'
    env:
      IMAGE_TAG: ${{ github.event.workflow_run.head_sha || github.sha }}
    steps:
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}
          aws-region: ${{ vars.AWS_REGION }}
      - id: ecr
        uses: aws-actions/amazon-ecr-login@v2
      - uses: docker/build-push-action@v7
        with:
          push: true
          tags: ${{ steps.ecr.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${{ env.IMAGE_TAG }}
      - run: envsubst < deploy/ecs/task-definition.json > task-definition.rendered.json
      - id: render
        uses: aws-actions/amazon-ecs-render-task-definition@v1
        with:
          task-definition: task-definition.rendered.json
          container-name: api
          image: ${{ steps.ecr.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${{ env.IMAGE_TAG }}
      - uses: aws-actions/amazon-ecs-deploy-task-definition@v2
        with:
          task-definition: ${{ steps.render.outputs.task-definition }}
          cluster: ${{ env.ECS_CLUSTER }}
          service: ${{ env.ECS_SERVICE }}
          wait-for-service-stability: true    # fails if the new task does not become healthy
```

The database URL is not in the repository either: the task definition points to a **Secrets Manager** ARN (`DATABASE_URL_SECRET_ARN`), and ECS injects it when the container starts.

## 4. docusaurus (this site)

```yaml title=".github/workflows/deploy.yml"
on:
  push: {branches: [main]}
  pull_request: {branches: [main]}
jobs:
  build:
    steps:
      - run: npm ci
      - run: npm run typecheck     # TypeScript of the React components
      - run: npm run build         # prebuild generates the docs-chat index, then 5 languages
      - if: github.event_name != 'pull_request'
        uses: actions/upload-pages-artifact@v3
        with: {path: build}
  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'
    permissions: {pages: write, id-token: write}
    steps:
      - uses: actions/deploy-pages@v4
```

If the **Deploy** job fails with a timeout, it is GitHub Pages being slow, not the site: open the run and click **Re-run failed jobs**.

## How to turn the deploys on

1. Open port 22 of the EC2 security group to GitHub Actions (their IPs change, so in this project it is open to `0.0.0.0/0` with key-only login).
2. In each repository: **Settings → Secrets and variables → Actions → New repository secret**. Pipeline: `DEPLOY_SSH_KEY`, `NUCLEO_HOST`, `WORKERS_HOST`. Sources: `DEPLOY_SSH_KEY`, `SOURCES_HOST`. api-reviews uses repository *variables* instead (`AWS_ROLE_ARN`, `AWS_REGION`, `ECR_REPOSITORY`, `ECS_CLUSTER`, `ECS_SERVICE`, …).
3. Push to `main` (or click **Run workflow**). The run shows `Deploy` in green and the step log shows the `docker compose` output of the server.

**How to check a run:** tab **Actions** of the repository → click the run → each job shows its steps; a red ❌ step has the exact error. A PR can only be merged when its checks are green.
